# jira-harness

**Краткое описание.** jira-harness — это бот, который берёт тикеты из Jira и
самостоятельно доводит их до готового merge request'а: анализирует задачу,
пишет код, прогоняет тесты/линтер/тайпчек, при необходимости повторяет
попытки с учётом ошибок, и в конце открывает MR в GitLab, переводя тикет в
статус ревью. Управляется через Telegram — слэш-командами и свободным
текстом — с живым веб-дашбордом для наблюдения за процессом. Граница
автономности задана жёстко: бот доходит до открытия MR и перевода тикета на
ревью — никогда не мержит сам и никогда не закрывает тикет.

## План сборки

0. Доступы/инфраструктура
1. **Базовый цикл на одну задачу (готово)** — доказать, что исполнение +
   верификация работают для одной задачи, без Jira/Telegram
2. **Очередь из Jira (готово)** — забрать один назначенный тикет из "To Do",
   отправить в back-ai/front-ai по префиксу `[backend]`/`[frontend]`,
   прогнать через цикл шага 1, запушить + открыть MR в GitLab, перевести
   тикет на ревью
3. **Telegram-бот (готово)** — `/start`/`/stop`/`/status` и другие команды,
   ведёт очередь по поллингу, считает стоимость по задаче
4. Учёт токенов/стоимости, сохраняется между задачами — встроено в шаг 3
   (`.harness-state/bot-state.json`)
5. **Живой веб-дашборд (готово)** — `/dashboard` в Telegram, только локально
6. **Гварды (готово)** — дневные лимиты бюджета/количества задач, механический
   deny-list для миграций/CI/секретов/lock-файлов
7. **Тесты и обязательное покрытие ими (готово)** — `npm test` + git-хуки,
   блокирующие коммит без тестов
8. **Свободный чат, модели по ролям, несколько гейтов верификации, checkpoint
   (готово)** — добавлено сверх первоначального плана
9. **Исполняемый слой acceptance-тестов (готово)** — критерии приёмки из
   шага propose превращаются в реальный тест, замороженный как строгий гейт
10. **Project memory между задачами (готово)** — долгоживущие факты/решения
    пишутся в `.claude/memory/jira-harness.md` и читаются в будущих задачах
11. **Детектор застревания (готово)** — повтор одинаковой ошибки гейта два
    раза подряд останавливает цикл раньше `MAX_ITERATIONS`
12. **Мини eval-набор (готово)** — реальные закрытые баги как воспроизводимый
    бенчмарк для сравнения моделей/промптов между собой
13. **Независимое ревью (готово)** — отдельный ход ловит то, что гейты не
    способны поймать механически (безопасность, архитектура, edge-кейсы)
14. **Оценка стоимости/времени до подтверждения (готово)** — предложение в
    Telegram показывает медианные $/минуты по истории похожих задач, прежде
    чем человек нажмёт "Подтвердить"
15. **Кросс-репо задачи (готово)** — тикет, помеченный и `[backend]`, и
    `[frontend]`/`[web]`, больше не пропускается: бэкенд реализуется первым,
    его реальный дифф передаётся фронтенду как контекст, оба MR открываются
    и связываются друг с другом
16. **Инструкция для тестировщика (готово)** — после успеха отдельный ход
    пишет Предусловия/Шаги/Ожидаемый результат и постит их комментарием в
    Jira рядом со ссылкой на MR
17. **Секреты вне окружения агента (готово)** — `JIRA_PAT`/`GITLAB_TOKEN`/
    `TELEGRAM_BOT_TOKEN` явно вычищаются перед запуском `claude`, чтобы
    промпт-инъекция не смогла прочитать их через Bash
18. **Проверка целостности гейтов (готово)** — механическая (без LLM)
    проверка ловит удаление тестов, skip-маркеры и правки CI/конфига гейтов
    — то, чем агент мог бы сам ослабить свой же судья
19. **Уборка worktree после закрытия (готово)** — worktree и локальная
    ветка больше не копятся на диске бесконечно после успешного MR
20. **Бюджет контекста сессии (готово)** — длинная задача останавливается
    и уходит к человеку до того, как раздувшийся контекст начнёт портить
    качество ответов агента
21. **Checkpoint покрывает push/MR/Jira (готово)** — окно "упал без единой
    записи о задаче" сократилось с полного push+MR+Jira-цикла до секунд
22. **Роли с раздельной памятью и цикл ревьюер↔разработчик (готово)** — PM/
    разработчик/ревьюер читают каждый свой файл памяти, а блокирующая находка
    ревью уходит на фикс разработчику (до `MAX_REVIEW_ROUNDS` раундов) вместо
    немедленной эскалации человеку
23. **"Зам. CEO" как персонаж (готово)** — бот переозвучен от лица одного
    персонажа вместо нейтрального диспетчера; данные те же, меняется только
    то, как они преподносятся
24. **Брифы (готово)** — разработчик больше не додумывает за человека: при
    реальной неоднозначности останавливается и присылает вопрос с вариантами,
    одним кликом в Telegram, и продолжает с тем же контекстом сессии
25. **Маскирование секретов в тексте роли (готово)** — известные секреты и
    характерные формы токенов/ключей вычищаются из ответа любой read-only
    роли, прежде чем он попадёт в Jira, MR или файл памяти проекта
26. **Свежая база перед новой задачей (готово)** — worktree новой задачи
    ветвится от только что зафетченного `origin/<targetBranch>`, а не от
    возможно устаревшего локального HEAD основного чекаута
27. **Метрики по истории (готово)** — `/metrics` агрегирует всю историю
    задач в `bot-state.json`: доля без эскалации, средние стоимость/время/
    раунды ревью, разбивка по репозиториям
28. **pass@1/pass^k для eval-набора (готово)** — `eval --k N` гоняет каждый
    кейс N раз вместо одного, конвенции pass@1 (среднее) и pass^k (прошли
    ВСЕ попытки) из Avengers Harness вместо единственного pass/fail
29. **Брифы в ревью-раунде и кросс-репо (готово)** — вопрос, поднятый
    fix-ходом внутри цикла ревью↔правка, и вопрос от любой половины
    кросс-репо задачи — теперь такой же one-click, как и в основном ходу
    реализации, не текстовый "нужен человек"
30. **Резюме больше не стирает незакоммиченную работу (готово, исправлен
    баг)** — `CloseLoopResumeState.worktreeDir` обязателен, резюме всегда
    переиспользует тот же worktree вместо повторного `createWorktree()`
31. **Свежая база при резюме (готово)** — пауза на бриф может длиться часы
    или дни; `rebaseOntoFreshBase()` перебазирует worktree на свежий
    `origin/<targetBranch>` при возобновлении, конфликт → "нужен человек"
32. **Резюме ревью-брифа больше не молчит при смене конфига (готово,
    исправлен баг)** — `reviewResumeNowUnsafe()` эскалирует к человеку,
    если `REVIEW_ENABLED`/`MAX_REVIEW_ROUNDS` поменяли, пока бриф висел,
    вместо того чтобы молча пропустить уже данный ответ и отрапортовать
    ложный "verified"
33. **Докладчик с отчётом (готово, без скриншотов)** — после закрытия
    отдельная read-only роль (`closeReport.ts`) пишет короткую сводку без
    технических терминов для заказчика тикета, показывается в закрывающем
    сообщении Telegram вместо голого "закрыто, вот MR"
34. **Текстовый отчёт вложением в Jira (готово)** — при переходе тикета из
    "В работе" дальше (ревью или вручную принятое "нужен человек") к нему
    прикрепляется файл с тем же докладом + инструкцией тестировщику, без
    дополнительного хода `claude` — переиспользует уже сгенерированный текст
35. **Закрыт обход gate'а подтверждения в `queue`/дашборде (готово,
    исправлен баг)** — `queue` CLI и кнопка "Запустить" в дашборде раньше
    запускали весь цикл (реализация → ревью → push → MR) напрямую, минуя
    подтверждение в Telegram целиком. Теперь оба — только `proposeNext`/
    `proposeIssueByKey`, тот же путь, что и `pick:` в Telegram; единственный
    путь к реальному исполнению — `confirmPending()`. Вместо `queue` на
    cron — `bot` теперь сам поллит Jira, пока запущен (см. раздел ниже)
36. **«Продолжить» после остановки по лимиту контекста (готово)** — задача,
    остановленная по `context_budget`, теперь не только "принять как есть"/
    "отклонить": третья кнопка в Telegram запускает ту же задачу заново
    свежей сессией, с текущим диффом вместо `--resume`'а старой сессии —
    осознанный компромисс (новая сессия не помнит, что уже пробовала
    старая), поэтому только по явному клику человека, никогда автоматически
37. **Неверный тег репозитория — не стоппер (готово)** — тикет, помеченный
    `[frontend]`, но по факту оказавшийся чисто бэкендовым (и наоборот),
    больше не превращается в "сообщить другой команде" вместо реального
    фикса: propose-ход умеет сказать `РЕПОЗИТОРИЙ: backend/frontend` вместо
    плана, харнесс сам переправляет тег в заголовке Jira-тикета и
    переанализирует задачу по правильному репозиторию
38. **Свободный чат больше не выдумывает своё поведение (готово, исправлен
    баг)** — вопрос "как/почему ты что-то делаешь" раньше получал от Haiku
    правдоподобно звучащий, но местами полностью выдуманный ответ (разный
    при одном и том же вопросе). Промпт теперь несёт реальные факты о
    механике (гейты/`MAX_ITERATIONS`, `stuck`, `context_budget`, брифы,
    ревью) — такие вопросы отвечаются только ими, без фантазии
39. **Закрыта гонка двойного анализа (готово, исправлен баг)** — ручной
    пик тикета и автополлинг могли оба пройти проверку "ничего не
    выполняется" одновременно, потому что она ничего не знала про сам
    анализ (несколько секунд до `setPendingApproval`) — оба реально
    анализировали (платно), оба слались в Telegram, выживал только
    последний. Новый флаг `LiveState.analyzing` выставляется синхронно
    сразу после проверки, до похода в Jira и хода `claude` — второй
    конкурентный вызов теперь видит "занято" мгновенно
40. **Диффы больше не путает устаревшая/уехавшая вперёд `dev` (готово,
    исправлены два бага)** — `getWorktreeDiff` (а с ним gate-integrity,
    ревью, memory, testing-notes, все диффы для человека) сравнивал против
    голого имени ветки, которое резолвится в ЛОКАЛЬНУЮ ветку в репо — она
    ничем не обновляется, кроме как при создании/ребейзе новой задачи, и
    отстаёт от `origin` всё сильнее. Поймано вживую: diff показал файл
    уже смерженного ДРУГОГО тикета как будто его только что добавили.
    Сравнение теперь идёт от `git merge-base HEAD origin/<ветка>` —
    единственной точки, которая не зависит ни от устаревания локальной
    ветки, ни от того, что `origin` уехал дальше с чужими коммитами
41. **gate-integrity больше не путает санкционированный `test.skip` с
    ослаблением теста (готово, исправлен баг)** — acceptance-test-writer
    намеренно пишет `test.skip(...)` для критериев, непроверяемых
    автотестом (почти всегда — "tsc/build проходят"), но механическая
    проверка целостности гейтов считала ЛЮБОЙ новый skip/only/todo
    нарушением без исключений — срабатывала почти на каждой задаче.
    Теперь единственный замороженный путь acceptance-теста исключён из
    проверки; skip/todo где угодно ещё — по-прежнему нарушение
42. **`eval --k 0` (или отрицательный/нечисловой) больше не притворяется
    PASS (готово, исправлен баг)** — `aggregateAttempts` считала среднее
    и `every(...)` по пустому массиву попыток; `average([])` — `NaN`,
    `[].every(...)` — истина по умолчанию, так что "вообще не запускался"
    выглядел неотличимо от "прошёл все попытки". Теперь `aggregateAttempts`
    бросает ошибку на пустом массиве попыток, а `cli.ts` валидирует `--k`
    (целое, ≥ 1) до запуска сьюта, вместо того чтобы долететь до этого как
    необработанный reject
43. **Пик тикета во время чужого анализа больше не выглядит как сбой
    (готово, исправлен баг)** — пойман вживую: пока анализ XEN-541 ещё
    шёл (гонка из пункта 39 корректно его держала), повторные `/start` →
    выбор тикета получали безликое "не удалось начать — попробуй ещё
    раз", что читалось как поломка и провоцировало новые попытки.
    Теперь колбэк выбора проверяет `analyzing` до плейсхолдера
    "Анализирую…" и сразу отвечает по имени ("XEN-541 уже анализируется —
    подожди"); тот же `busyWith` (новая функция `whatsBusy`) используется
    и в узком остаточном окне гонки внутри `proposeIssueByKey`
44. **`agent_error` больше не молчит о причине (готово, исправлен баг)** —
    пойман вживую на XEN-541: это был единственный stopReason, для
    которого не строилось содержательное сообщение (`stuck`/
    `review_blocked`/`gate_integrity_violation`/`context_budget`/
    `rebase_conflict` — у всех есть). Причиной оказался реальный хит
    лимита сессии Claude ("You've hit your session limit"), но в Jira/
    Telegram долетало только голое слово `agent_error`. Логика сборки
    причины вынесена в чистую `buildFailureReason` (переиспользуется и
    кросс-репо путём) и теперь для `agent_error` подставляет `resultText`
    упавшего хода
45. **Backend test-гейт больше не гоняет весь бэкенд на каждой итерации
    (готово, ускорено)** — `yarn test` на `back-ai` — 1211 файлов, 45+
    минут, причём на baseline И после каждой fix-попытки. Первая попытка
    (`jest --findRelatedTests`) провалилась: граф зависимостей NestJS
    зацепил 275+ несвязанных сьютов через общий `llm-router`. Новый
    `scripts/scoped-test-backend.sh` сужает по ДИРЕКТОРИИ изменённых
    файлов (путь-паттерн jest, не обход графа) и, по явному запросу
    пользователя, оставляет только unit-тесты — свой `find`,
    исключающий `*.integration.spec.ts` (реальные БД/инфра-тесты, не
    unit). На реальном диффе 45+ минут стали 2-4 секунды. Гейт помечен
    `strict: true` (`BACKEND_TEST_STRICT`), потому что у diff-scoped
    гейта baseline всегда пуст (ничего не менялось на момент baseline) —
    сравнивать не с чем, нужен честный "прошло/не прошло". Заодно
    `establishBaselines` теперь вообще не гоняет strict-гейты (их
    baseline всё равно никогда не читается — раньше впустую прогонялся
    и acceptance-гейт тоже). Отдельно найден и намеренно НЕ обойдён баг
    jest/yargs: ЛЮБОЕ значение `--testPathIgnorePatterns` через CLI
    молча ломает позиционный путь-паттерн (воспроизведено на реальном
    карантине, на фейковом множественном паттерне и на одном-единственном
    реальном паттерне — дело в самом флаге, не в количестве/содержимом) —
    поэтому и исключение `.jest-quarantine`, и unit/integration-фильтр
    реализованы через явный список файлов (`find ... ! -name`), а не
    через этот флаг
46. **`agent_error` без деталей при обрыве по бюджету хода (готово,
    исправлен баг)** — пойман вживую на XEN-540: обрыв по
    `--max-budget-usd` оставлял поле `result` от CLI ПУСТЫМ, хотя модель
    уже успела написать полноценный статус-отчёт (что сделано, что нет,
    почему) последним текстовым блоком — `buildFailureReason` (пункт 44)
    откатывался на голое слово не потому, что сказать было нечего, а
    потому что `resultText` был пуст. Новая `pickResultText` в
    `claudeEngine.ts` подставляет последний текстовый блок ассистента,
    когда `result` от CLI пуст
47. **`agent_error` теперь резюмируем, как `context_budget` (готово,
    новая возможность)** — пойман вживую: XEN-540/XEN-541 упирались в
    лимит сессии аккаунта или в бюджет хода, и обе попытки терялись
    безвозвратно — `resumeState` ставился только для `context_budget`/
    `brief_pending`, так что "🔄 Продолжить" для `agent_error` не
    появлялась вообще, и реальная частичная работа (схема, core-логика)
    выбрасывалась на каждый повтор. Теперь оба места возврата
    `agent_error` в `loop.ts` тоже ставят `resumeState` — но, в отличие
    от `context_budget` (`freshSession: true`, размер контекста и был
    причиной), через `--resume` той же сессии: ни лимит аккаунта, ни
    обрыв по бюджету хода не говорят, что рассуждения сессии были
    проблемой. Кнопка в `bot.ts` подписывается по месту: "Продолжить
    (новая сессия)" только когда `resumeState.freshSession` стоит
48. **`closeLoopAndPush`/`handleCloseLoopOutcome` экспортированы для
    ручного вмешательства с точным промптом (готово, операционный
    инструмент)** — пойман вживую на XEN-540: `continueNeedsHuman`'s
    собственный `buildContinuationPrompt` ("вот весь диф, перепроверь
    по каждому критерию") дважды подряд спалил весь бюджет свежей сессии
    на широкое само-ревью, ни разу не дойдя до единственной правки,
    которая реально требовалась (одна строка). Явный `buildFeedbackPrompt`
    с точным текстом гейта вместо этого решил проблему за один ход и
    четверть доллара. `continueNeedsHuman` сам по себе не менялся (общий
    случай); это — осознанный люк для случаев, когда он не справляется
49. **XEN-540 закрыт** (`merge_requests/532`) — ролевая изоляция прав для
    подпапки со специфичными ACL. Тест приёмки 6/6 (миграция — 7-й
    критерий — намеренно не создана, ждёт отдельного "да" от человека).
    Два оставшихся "провала" test-гейта и все ошибки build/typecheck
    подтверждены как предсуществующие (идентичны на чистом `dev` без
    диффа) — независимая проверка на throwaway-ветке от merge-base,
    не само-отчёт сессии
50. **`context_budget` больше не срабатывает ложно (готово, исправлен баг)** —
    размер контекста считался по `usage` result-события CLI, а оно
    суммируется по всем API-вызовам хода: ход из 66 вызовов с реальным
    контекстом 187k отчитывался как 8783k. Все четыре остановки XEN-540 и
    "реальные значения 983k-2595k", по которым выставлялся порог, были
    этими суммами. Теперь берётся usage последнего API-вызова из потока
    (`callContextTokens`); порог возвращён к осмысленным 160k
51. **Вывод упавших гейтов переживает `context_budget` (готово, исправлен
    баг)** — гейты на остановленном ходе запускались и ловили ошибку, но
    до человека и до следующей сессии доходило только число токенов:
    три свежие сессии подряд перепроверяли весь диф, не зная, что сказал
    компилятор. Упавшие гейты теперь лежат в `resumeState.failedGates`,
    идут первым разделом в промпт продолжения и названы в причине.
    Возобновление той же сессии после `agent_error` получает свой короткий
    промпт вместо ложного "ты новая сессия"
52. **Стоимость продолжений не учитывается повторно (готово, исправлен
    баг)** — каждое продолжение писало в историю накопленную сумму задачи
    новой записью (XEN-540: 10.14 → 10.23 → 13.02 → 16.97 → 19.50), и
    `costToday` показал $47 при ~$25 реальных, ложно упираясь в дневной
    лимит. Исход продолжения несёт `costAlreadyRecordedUsd`, в историю
    идёт только прирост (`outcomeToRecord`)
53. **Гейты больше не отключаются молча и не виснут (готово, исправлены
    баги)** — гейт, упавший по памяти или таймауту, записывал baseline
    "красный, не подсчитать", после чего проходил всегда (на XEN-540 так
    были фактически выключены typecheck и build). Теперь это
    `GateInfraError` после одной повторной попытки: задача уходит человеку
    с причиной, а не едет дальше вслепую. Гейтам подняли heap, добавили
    таймаут (`GATE_TIMEOUT_MS`, 30 мин) и парсер для build; им же теперь
    передаётся окружение без секретов харнесса
54. **Test-гейт бэкенда сравнивает с базовым коммитом (готово)** —
    `scripts/scoped-test.mjs` заменил shell-скрипт: упавшие spec-файлы
    перезапускаются во временном worktree на merge-base, и гейт падает
    только на НОВЫХ падениях. Раньше любая задача рядом с уже сломанным
    тестом (в `modules/documents` их десять) не могла закрыться сама.
    Проверено вживую: 54 файла, 10 старых падений отсеяны, 31 секунда;
    намеренно сломанный тест ловится
55. **Ревью больше не пропускает при собственном сбое (готово, исправлен
    баг)** — ошибка хода, лимит сессии или ответ не в формате давали ноль
    замечаний, то есть "ревьюер доволен", и шёл push. Теперь одна
    повторная попытка, затем `review_blocked`. Лимит диффа для ревьюера
    поднят с 8k до 60k символов со списком файлов при обрезке
56. **Прочее в движке (готово)** — детектор зацикливания смотрит на строки
    с ошибками, а не на первые три строки вывода (одинаковый баннер делал
    два разных падения "зацикливанием"); проверка целостности гейтов
    ловит `.only`, jest-конфиг внутри `package.json`, `tsconfig`,
    `.jest-quarantine`, удаление строк из конфигов и переименование
    тест-файла; вспомогательные ходы (ревью, заметки, память) ограничены
    остатком бюджета задачи; предупреждение, если `node_modules` основного
    чекаута отстал от lock-файла
57. **Сбой больше не оставляет задачу без хозяина (готово, исправлены
    баги)** — состояние ожидания стиралось до начала работы и не
    возвращалось при исключении: упавший push, убитый ход или сбой Jira
    после открытия MR оставляли worktree без кнопок и тикет "В работе".
    Теперь любое исключение после создания worktree превращается в
    `needs_human` с диффом (`escalateFailure`), а неудавшиеся
    принять/продолжить/ответ на бриф возвращают состояние как было.
    Комментарии и переходы в Jira стали best-effort — они не могут
    сорвать уже сделанную работу
58. **`/kill` действительно останавливает (готово, исправлен баг)** —
    один слот под "текущий процесс" затирался чат-классификатором и
    параллельными ходами, а гейты не отслеживались вовсе. Общий реестр
    процессов (`processRegistry.ts`) останавливает и ходы, и гейты целой
    группой процессов; прерванный ход возвращается как резюмируемый
    `agent_error`, а не как необработанная ошибка. Проверено вживую локальным
    прогоном всего движка. Заодно: stdin хода закрыт явно — CLI ждал по
    3 секунды несуществующего ввода на каждом ходе
59. **Прочее в оркестрации (готово)** — продолжения проверяют дневной
    бюджет; лимит задач в день считает тикеты, а не записи; тег в
    заголовке тикета главнее тегов в описании; переход в уже текущий
    статус Jira — не ошибка; повторный push в свою ветку и уже открытый
    MR больше не валят задачу; числовые настройки с опечаткой
    останавливают запуск, а не отключают лимит; битый файл состояния
    откладывается в сторону, запись атомарная; дашборд слушает только
    localhost и сообщает, почему "Предложить" не сработало
60. **Сообщения с кнопками всегда доходят (готово, исправлены баги)** —
    Telegram отклоняет сообщение длиннее 4096 символов целиком, вместе с
    кнопками: длинная причина остановки плюс дифф или длинный план
    предложения не доставлялись, ошибка глоталась, и задача ждала
    человека, которому ничего не пришло. Все исходящие тексты теперь
    подгоняются под лимит, а отправка деградирует по шагам (полный текст →
    простой обрезанный → строка со ссылкой на `/status`), сохраняя кнопки
61. **Прочее в боте (готово)** — `/status` показывает, что реально
    выполняется (задача, фаза, итерация), а не только флаг автопоиска;
    ручное принятие пишется в историю как закрытая задача; неизвестная
    команда и внутренняя ошибка получают ответ; второй экземпляр бота не
    запускается (`bot.lock`), а `queue` отказывается работать поверх
    живого бота; несколько прерванных задач восстанавливаются по очереди,
    не затирая друг друга; дашборд экранирует весь текст тикетов
62. **Суженный тест-гейт для фронта (готово)** — `scripts/scoped-test.mjs`
    сам определяет раннер: есть `vitest.config.*` — Vitest (front-ai), иначе
    Jest (back-ai); оба пишут один и тот же JSON-отчёт, сравнение с базовым
    коммитом общее. На front-ai: 34 файла тестов за ~9 с вместо полного
    `yarn test` на 715 файлов. `git fetch` внутри гейта ограничен 20 с —
    медленный GitLab однажды держал гейт семь минут
63. **Репозитории задачи определяются по коду, а не по тегу (готово)** —
    `src/engine/repoScope.ts`: на этапе анализа идут два параллельных
    read-only хода, по одному на репозиторий; каждый планирует свою часть и
    может читать второй репозиторий (`--add-dir`), чтобы проверить стык
    (эндпоинт, поле, контракт). Ход отвечает либо планом с критериями, либо
    строкой `ИЗМЕНЕНИЯ: НЕ НУЖНЫ — <причина>`. Оба с планом → задача идёт
    как кросс-репо (бэкенд → фронтенд, два MR); один → только он, а в
    предложении написано, какой репозиторий не трогается и почему; ни один →
    тикет пропускается. Теги `[backend]`/`[frontend]` в заголовке больше ни
    на что не влияют (тикет без тега тоже берётся), запуск идёт по объёму из
    одобренного предложения. Раньше тикет с одним тегом делался только в
    одном репозитории, даже если без правок во втором фича не работала
64. **`/start` больше не берёт задачу сам (готово)** — раньше `/start`
    показывал список и заодно включал автопоиск, который через 10 секунд
    брал верхний тикет очереди на анализ, не дождавшись выбора (XEN-632).
    Теперь `/start` только показывает список и ждёт; автопоиск включается
    отдельной командой `/auto`, выключается `/stop` или `/kill` и после
    перезапуска бота всегда выключен
65. **Разбор анализа репозиториев (готово, найдено на XEN-632)** — строка
    `ИЗМЕНЕНИЯ: НЕ НУЖНЫ` распознаётся на любой строке ответа, а не только
    на первой (модель писала абзац рассуждений перед ней, и фронтенд попадал
    в объём чисто бэкендовой задачи); рассуждения перед `ПЛАН:` вырезаются из
    плана, который видит человек
66. **Продолжение задачи после паузы не падает на новых файлах (готово,
    найдено на XEN-381)** — diff для ревью регистрирует новые файлы как
    intent-to-add, а `git rebase --autostash` такие записи спрятать не может:
    продолжение сразу заканчивалось ложным «rebase_conflict». Перед
    rebase индекс сбрасывается (`git reset`), файлы остаются как есть
67. **Понятные сообщения бота (готово)** — `src/bot/messages.ts`: каждое
    сообщение по задаче начинается с категории и тикета (`📋 ПРЕДЛОЖЕНИЕ ·
    XEN-381`, `🛠 В РАБОТЕ`, `❓ ВОПРОС`, `⚠️ НУЖНО ТВОЁ РЕШЕНИЕ`, `✅ ГОТОВО`,
    `🔄 НАПОМИНАНИЕ` …). Остановка объясняется словами (`explainStop`) вместо
    сырого кода и вывода git, вместо diff — список файлов с итогом +/−, под
    каждой кнопкой написано, что она сделает; «Выбросить» спрашивает
    подтверждение. Предложение короткое: где, что сделаю (одна фраза от
    анализа — строка `КОРОТКО:`), сколько критериев, стоимость; полный план и
    критерии — в свёрнутом блоке. Кнопки: «▶️ Взять в работу / ✖️ Не брать»,
    «🚀 Открыть MR / 🔄 Доработать / 🗑 Выбросить»
68. **Ход работы каждые 5 минут (готово)** — `src/bot/progress.ts`: пока идёт
    задача, одно сообщение `🛠 В РАБОТЕ` обновляется раз в 5 минут: что агент
    делает сейчас (одна фраза от дешёвой модели по его последним действиям,
    при сбое — последний файл), этап, попытка, время, расход
69. **Кнопка «🛠 Решить самому» (готово)** — на любой остановке задачи бот
    может разобраться сам: у каждой остановки теперь есть состояние для
    продолжения (`withFixResumeState` в `loop.ts`), и новая сессия агента
    получает первым абзацем, что именно пошло не так (`engine/fixPrompts.ts`):
    замечания ревью — исправить их; ослабленные проверки — вернуть как было;
    застрял/кончились попытки — не повторять прежний подход; конфликт с dev —
    бот вливает свежий dev в ветку (`mergeFreshBase`: конфликт коммитится с
    маркерами, ветка никогда не остаётся посреди слияния), агент убирает
    маркеры. Сбой пуша/MR просто повторяется. Запуск получает новый бюджет
    `MAX_BUDGET_USD` поверх уже потраченного и полный счётчик попыток.
    Для половин кросс-репо задачи кнопки нет (как и раньше «Продолжить»)
70. **Лимиты подняты (готово)** — `MAX_BUDGET_USD` 20→40,
    `CONTEXT_BUDGET_TOKENS` 160k→400k (окно модели разработчика — 1M, 160k
    останавливал реальные задачи на середине), `MAX_ITERATIONS` 5→8,
    `DAILY_BUDGET_USD` 150

## Дизайн шага 1, и почему он так выглядит

Движок управляет CLI `claude` в headless-режиме (`-p --output-format json`),
не через SDK и не через `--bg`. Три вещи, выясненные тестированием на реальном
CLI, а не предположенные:

- **ECC обязательно отключить глобально** (`claude plugin disable ecc`).
  Установленный на уровне пользователя, его хуки матчатся только по имени
  инструмента (`Write`, `Edit`, `Bash`, `.*`) без привязки к проекту, поэтому
  срабатывают в любой сессии, включая headless-прогоны харнесса. Один из
  хуков интерактивный (показывает факты, ждёт ответа) — без человека в
  фоновой сессии он виснет навсегда. `--bare` выглядел как решение, но не
  подходит: принимает только `ANTHROPIC_API_KEY`, а не подписочный/OAuth-логин
  этого аккаунта.
- **Агент никогда не запускает Bash.** Даже `--permission-mode
  bypassPermissions` не даёт безнадзорного выполнения shell-команд в headless
  `-p` режиме — классификатор Auto Mode у Claude Code стоит перед системой
  разрешений и блокирует независимо от неё (подтверждено вживую: тривиальный
  `echo` был отклонён с "Blocked by classifier"). Вместо борьбы с этим слоем
  агент получает `--disallowedTools Bash` и только редактирует файлы; git
  (коммит, а позже push/MR) делает собственный доверенный код харнесса,
  никогда не модель. Это также соответствует инстинкту ADR-1 у DEVBOT
  (инфраструктурные действия не доверяются модели), хотя здесь исполнение
  происходит локально, а не в CI.
- **Каждая задача работает в своём `git worktree`**, а не в ветке, зачекаученной
  в общей рабочей копии. Нужно для безопасного параллелизма позже (шаг 2+
  гоняет несколько задач) и не даёт зависшей/неправильно ведущей себя задаче
  затронуть основной чекаут.

Верификация — это внешняя shell-команда (например `pnpm test`), запускаемая
харнессом напрямую через `child_process`, никогда агентом — чтобы результат
"прошло" не мог быть неподтверждённым заявлением самой модели.

## Использование

### Шаг 1: разовая задача в любом репозитории

```bash
npm run build
node dist/cli.js run \
  --repo /path/to/target/repo \
  --task '{"id":"XEN-1","title":"...","description":"...","acceptanceCriteria":["..."]}' \
  --verify "pnpm test" \
  --max-iterations 5 \
  --max-budget-usd 5
```

`--task` также принимает путь к `.json`-файлу с той же структурой, или просто
строку (воспринимается как произвольное описание задачи без id/критериев). В
конце вывода — путь к worktree и имя ветки с закоммиченным фиксом; ничего не
пушится.

### Шаг 2: очередь из Jira

```bash
cp .env.example .env   # заполните JIRA_PAT и GITLAB_TOKEN, проверьте названия статусов
npm run build
node dist/cli.js queue
```

Каждый запуск берёт один тикет с наивысшим приоритетом, назначенный на вас в
"To Do", переводит в "In Progress", прогоняет через цикл шага 1 в том
репозитории, на который указывает префикс `[backend]`/`[frontend]`, и при
успехе пушит ветку и открывает MR в GitLab, после чего переводит тикет в
статус ревью. Тикет остаётся "In Progress" с поясняющим комментарием (не
повторяется молча), если: роутинг неоднозначен (нет префикса), цикл не прошёл
верификацию, или не удался push/MR — это требует взгляда человека, а не ещё
одной автоматической попытки.

Запускайте `queue` по таймеру (cron, `watch`, или Telegram-бот из шага 3),
чтобы реально разгружать очередь — один вызов обрабатывает ровно один тикет.

### Шаг 3: Telegram-бот

```bash
# в .env: TELEGRAM_BOT_TOKEN (от @BotFather), TELEGRAM_ALLOWED_CHAT_IDS
# (ваш числовой chat id, от @userinfobot — через запятую, если их несколько)
npm run build
node dist/cli.js bot
```

`TELEGRAM_ALLOWED_CHAT_IDS` — это жёсткий allowlist, а не удобство по
умолчанию: бот может пушить код и открывать MR, поэтому он молча отбрасывает
команды из любого чата не из списка, вместо того чтобы раскрывать себя кому
попало.

**Бот говорит от лица одного персонажа — "Зам. CEO".** Это не новая
архитектура, а переозвучка существующего интерфейса: та же логика, те же
реальные данные (стоимость, план, diff — ничего не придумывается и не
меняется), просто вся текстовая обёртка написана так, будто с тобой
переписывается конкретный человек, который ведёт эти тикеты, а не
бот-диспетчер. Сильнее всего это заметно в свободном чате (`classifyMessage`
ниже) — там модель отвечает от первого лица, но по-прежнему не имеет права
придумывать цифры бота: вопрос про расход/статус/очередь всегда уходит
соответствующей команде за настоящими данными, а не угадывается текстом.

Числа — не единственное, что модель может придумать. Reproduced live: вопрос
"что будешь делать, если задача окажется слишком сложной?" дал два РАЗНЫХ
ответа подряд — один раз честно описал реальную эскалацию, второй раз
сфантазировал несуществующее поведение ("делю на подзадачи, ищу аналоги в
кодбейсе"). `classifyMessage` (Haiku — дешёвая и быстрая модель для
классификации, не рассчитана на точность) не знала реальную механику и
просто сочиняла правдоподобный ответ заново на каждый вызов. Промпт теперь
несёт короткий список настоящих фактов о том, как харнесс на самом деле
ведёт себя (гейты/`MAX_ITERATIONS`, `stuck`, `context_budget`, брифы,
независимое ревью, варианты решения при остановке) — вопрос "как/почему ты
что-то делаешь" обязан отвечаться только этими фактами, не додумывая сверху.

- `/start` — показывает все тикеты, назначенные на вас, в "To Do" *и* "In
  Progress" (чтобы тикет, уже взятый вручную или оставленный на середине,
  оставался видимым), по одной инлайн-кнопке на тикет. **Сам по себе ничего не
  выбирает.** Нажатие на кнопку запускает read-only ход только по этому
  тикету (Edit/Write/Bash запрещены — подтверждено вживую: ноль изменений
  файлов, только короткий план) и отправляет сообщение с описанием тикета,
  предложенным решением, **списком критериев приёмки** и инлайн-кнопками
  **✅ Подтвердить / ❌ Отменить**. Критерии — это контракт: модель формулирует
  их на этом же read-only ходу, вы видите их до начала работы, и при нажатии
  "Подтвердить" они замораживаются в задаче и превращаются в настоящий
  исполняемый тест (см. "Исполняемый слой acceptance-тестов" ниже) — цикл
  реализации их только читает как контекст, переписать не может (`TaskSpec`
  после диспетчеризации больше не меняется, а сам тестовый файл агенту
  редактировать механически запрещено). Снижает scope drift. Сам цикл (тот же
  пайплайн — worktree, верификация, push, MR, ревью) стартует только после
  нажатия "Подтвердить". "Отменить" записывает (небольшую)
  стоимость анализа в бюджет и пропускает этот тикет до конца жизни процесса,
  чтобы он не предлагался снова сразу же. Одновременно висит только одно
  предложение; выбор другого тикета, пока одно уже ожидает решения,
  отклоняется до его разрешения.
- `/status` — текущее состояние, стоимость за всё время и за сегодня,
  последний обработанный тикет.
- `/metrics` — трек-рекорд по ВСЕЙ истории, не по сегодняшнему дню: доля
  задач, закрытых без эскалации в "нужен человек", средняя/медианная
  стоимость и время тикет→MR, среднее число раундов ревью на закрытую задачу,
  разбивка по репозиториям. `null`, пока в истории нет ни одной `closed`/
  `needs_human` задачи — не нулевые цифры, а явное "рано считать".
- `/stop` — деактивирует кнопки у тикетов, уже показанных через `/start`
  (вызовите `/start` заново для свежего списка); даёт текущей работе доехать
  до конца, а не убивает её на середине.
- `/kill` — немедленно шлёт SIGTERM текущему ходу `claude`, когда он завис или
  делает что-то нежелательное. Прерванная задача проявляется как ошибка
  очереди, а не молча исчезает.
- `/budget` — сегодняшние траты и количество задач относительно
  `DAILY_BUDGET_USD` / `MAX_TASKS_PER_DAY`, и лимиты на задачу.
- `/peek` — показывает, какой тикет будет взят следующим (ключ, краткое
  описание, в какой репозиторий роутится, первые 1000 символов описания), не
  переводя его в работу и ничего не тратя.
- `/retry XEN-123` — возвращает тикет, застрявший в "нужен человек", обратно в
  статус очереди, после того как вы устранили то, что его заблокировало
  (например, добавили недостающий префикс `[backend]`/`[web]`).
- `/help` — список всего вышеперечисленного.
- **Свободный текст** — помимо команд, боту можно писать обычным текстом:
  небольшая классифицирующая модель (Haiku) определяет намерение и либо
  вызывает тот же обработчик, что и соответствующая слэш-команда (поэтому
  ответ с реальными цифрами — статусом, бюджетом — никогда не может быть
  галлюцинацией модели, она лишь выбирает, какую команду вызвать), либо
  отвечает как обычный чат. Команды и свободный текст работают параллельно,
  не заменяя друг друга.

После закрытия или отклонения любой задачи (мерж, "нужен человек", отмена)
бот сам присылает обновлённый список тикетов — не нужно вызывать `/start`
вручную перед каждой следующей задачей.

Состояние (история, флаг "запущено") сохраняется в
`.harness-state/bot-state.json` между перезапусками бота.

### "Нужен человек": ревью диффа прямо в Telegram

Если цикл исчерпал итерации или не смог запушить/открыть MR, бот не
выбрасывает проделанную работу — он присылает сам diff (обрезанный, если
слишком длинный) с кнопками **✅ Принять и запушить / ❌ Отклонить**.
"Принять" коммитит то, что осталось незакоммиченным, пушит и открывает MR тем
же путём, что и обычный успех. "Отклонить" удаляет worktree и возвращает
тикет в "To Do". Если бот перезапустится, пока решение не принято — оно
восстановится из `.harness-state/pending-state.json` и придёт повторным
уведомлением.

### Исполняемый слой acceptance-тестов

Зафиксированные критерии приёмки — не просто текст в промпте. Сразу после
подтверждения, ещё до первой итерации `implement`, отдельный ход пишет РОВНО
ОДИН новый тестовый файл (`src/__acceptance__/<ISSUE-KEY>.<ext>`), по одному
`it()`/`test()` на каждый критерий — сначала изучив 2-3 существующих теста в
репозитории, чтобы использовать те же конвенции (моки, настройка тестового
модуля). Тест в этот момент обязан падать: реализации ещё нет, это не ошибка.

Дальше он становится **строгим** гейтом (`acceptance`) — в отличие от
typecheck/lint/test/build, которые сравниваются с baseline ("не хуже, чем
было"), этот обязан дать честный exit 0, иначе он никогда бы не заблокировал
ничего (при baseline-сравнении "осталось так же плохо, как было" засчиталось
бы проходом). Сам файл при этом механически недостижим для `implement` —
добавляется в тот же deny-list, что миграции и `.env` (см. шаг 6), так что
агент физически не может переписать тест под свою реализацию вместо того,
чтобы исправить код.

Механически проверяется, что ход действительно создал РОВНО этот один файл и
ничего больше не тронул (`git status --porcelain --untracked-files=all` после
хода) — если модель отклонилась от мандата, попытка целиком откатывается
(`git checkout -- . && git clean -fd`) и цикл продолжает работу уже без
acceptance-гейта, а не заваливает всю задачу из-за сбоя вспомогательного шага.

Команда запуска собирается как `<ACCEPTANCE_RUNNER> <путь-к-файлу>` —
`npx jest`/`npx vitest run` напрямую, а не через `yarn test`: живой прогон
показал, что `yarn test` на одном из репо попутно переписывает
`packageManager` в `package.json` (побочный эффект yarn 1.x), а это гейт,
который выполняется на каждой итерации — такой шум просочился бы в итоговый
коммит фикса.

Переменные: `ACCEPTANCE_MODEL` (по умолчанию Sonnet — нужно реальное
понимание кода, но один ограниченный ход, не открытый цикл),
`*_ACCEPTANCE_RUNNER`/`*_ACCEPTANCE_TEST_EXT` на репозиторий (расширение
должно совпадать с тем, что реально discover-ит тест-раннер репозитория —
`.spec.ts` для jest с `rootDir: src`, `.test.ts` для vitest с `include`).
Общий выключатель `ACCEPTANCE_TESTS_ENABLED` (по умолчанию `true`) отключает
весь слой разом, без правки гейтов/моделей выше.

### Project memory: заметки между задачами

Каждая задача по умолчанию стартует в вакууме — ничего не знает о предыдущих.
После успешной верификации и коммита отдельный read-only ход (как `propose` —
модель ничего не пишет на диск сама, только возвращает текст) решает, есть ли
здесь **долгоживущий** факт, решение или грабли, которые сэкономят время в
будущих задачах этого же проекта — неочевидное поведение стороннего сервиса,
причина архитектурного решения, повторяющийся источник ошибок. Пересказ самого
диффа или факт «задача закрыта» намеренно не считаются поводом для записи:
на живых прогонах модель корректно отвечает "ничего не записываю" для
тривиальных правок и реальных пограничных случаев, не раздувая файл шумом.

Если факт найден, харнесс сам пишет файл (не больше 150 строк, старое
заменяется, а не копится) и коммитит это отдельным коммитом на той же ветке —
видно в MR, не бэкдором мимо ревью.

**Память — отдельная на роль, не одна общая.** `propose` (PM) читает и видит
только `<repo>/.claude/memory/jira-harness/pm.md`, `implement` (разработчик) —
только `dev.md`, независимое ревью — только `reviewer.md` (сейчас в этот файл
никто не пишет, но роль под него уже выделена). Заметки PM про то, как в этом
проекте обычно формулируют тикеты, не должны просачиваться в то, что читает
ревьюер перед тем, как судить дифф, и наоборот — каждая роль видит только
свой файл. Сегодня пишет только `implement` (единственный ход, после
которого есть реальный diff, откуда факт может появиться), но разделение уже
на месте, когда появится свой писатель у PM/ревьюера.

Отдельно — если в репозитории уже есть свой, по-настоящему ведущийся
`.claude/memory/MEMORY.md` (как во `front-ai`: открытые эпики, «не трогать»,
ожидание ответа от бэка), харнесс читает его как контекст **и никогда не
пишет туда** — автоматический процесс не должен редактировать то, что активно
курирует команда. Он даже не подгружается в сессию автоматически (в
`CLAUDE.md` через `@import` идёт только `AGENTS.md`), так что без этого чтения
агент мог бы вообще не знать о таких предупреждениях.

Переменные: `MEMORY_MODEL` (по умолчанию Sonnet), общий выключатель
`MEMORY_ENABLED` (по умолчанию `true`).

### Модели по ролям

Каждая роль в пайплайне использует свою модель, настраивается отдельными
переменными окружения:

- `CHAT_MODEL` (по умолчанию Haiku) — классификатор свободного текста в
  Telegram: нужна скорость и дешевизна, не глубокое рассуждение, срабатывает
  на каждое случайное сообщение.
- `PROPOSE_MODEL` (по умолчанию Sonnet) — read-only анализ тикета и короткий
  план перед апрувом.
- `IMPLEMENT_MODEL` (по умолчанию Opus) — сам цикл правок и верификации;
  здесь цена более слабой модели (худший дифф) перевешивает разницу в
  стоимости.

### Шаг 5: живой дашборд

`/dashboard` в Telegram отвечает кнопкой "Open dashboard", ведущей на
`http://localhost:4790` (`DASHBOARD_PORT`). Сервер стартует автоматически
вместе с ботом (`node dist/cli.js bot`), или отдельно для тестирования через
`node dist/cli.js dashboard`.

Показывает одну задачу, которая сейчас в работе — очередь обрабатывает
тикеты по одному, так что это одна карточка прогресса, а не сетка нескольких
агентов: ключ тикета, заголовок, репозиторий, фаза
(transitioning/iterating/verifying/pushing/opening_mr/commenting), итерация
N/max, стоимость на текущий момент, прошедшее время, описание тикета
(свёрнуто), прокручивающийся живой лог того, что агент реально делает
(`Edit <file>`, `Grep "<pattern>"`, собственная озвучка — стримится по мере
появления через `--output-format stream-json`, а не опрашивается постфактум)
— плюс последние 20 завершённых задач (исход, ссылка на MR или причина,
стоимость, время). Опрашивает `/api/state` каждые 2 секунды; без авторизации,
так как привязан только к localhost.

**Список тикетов + ручной запуск.** Панель "следующие на очереди" показывает
всё, что сейчас назначено на вас в статусе очереди для подбора (тот же пул
тикетов, из которого берут `/peek` и автовыбор бота), с описанием и
определённым репозиторием для каждого, обновляется каждые 15 секунд
(`GET /api/tickets`, кэшируется на этот срок — это реальный поиск по Jira, не
бесплатно опрашивать его каждые 2 секунды). Клик по **Start** на тикете
(`POST /api/tickets/:key/start`) запускает именно этот тикет через тот же
пайплайн цикл/push/MR/перевод-на-ревью, что и автовыбор — это "запустить вот
этот прямо сейчас" поверх очереди, а не отдельный механизм: те же лимиты
бюджета, те же правила роутинга, те же гварды. Тикет, чей префикс никуда не
роутится, показывается в списке, но его кнопка Start отключена. Одновременно
выполняется только одна задача; клик по Start, пока что-то уже в работе,
отклоняется с 409 ещё до обращения к Jira.

**Пиксель-арт сцена** наверху — пародия на "Тайную вечерю": девять фигур в
мантиях в зале со стрельчатыми окнами и гобеленами, сидящие за длинным столом
под скатертью (ближе к композиции картины, чем первый упрощённый вариант:
индивидуальные цвета волос/бороды, разные цвета мантий/акцентов, визуально
выделенная центральная фигура). В режиме ожидания (в очереди пусто): каждая
фигура подносит свою кружку ко рту в собственном независимом ритме — обедают.
В работе: плитка-документ переходит из рук в руки вдоль стола по кругу, а две
фигуры, которые её сейчас передают, нарисованы с вытянутыми друг к другу
руками. Чистый пиксель-арт через canvas `fillRect` (без картинок-ассетов, без
библиотек), перерисовывается каждые 90мс; режим определяется тем, установлено
ли `live.currentJob` в том же опросе `/api/state`, который использует вся
остальная страница. Проверено скриншотом реально отрендеренной страницы через
headless Chrome, а не просто чтением кода.

**Интерфейс**: полностью на русском (и дашборд, и ответы бота), организован
во вкладки — Текущая задача / Очередь / История — с однострочной подсказкой
под панелью вкладок, объясняющей, что показывает каждая, вместо одной длинной
страницы.

Работает только с той же машины, на которой запущен бот — ссылка на
`localhost`, поэтому Telegram Desktop там открывает её в браузере по
умолчанию. Доступ с телефона потребовал бы туннель (ngrok/cloudflared), что
не настроено.

### Шаг 6: гварды

Два независимых слоя, проверяются в разные моменты:

- **Дневные лимиты** (`DAILY_BUDGET_USD`, `MAX_TASKS_PER_DAY`) —
  `runQueueOnce` проверяет сегодняшние траты/количество задач против этих
  значений *до* любого обращения к Jira, чтобы лимит никогда не оставил
  тикет застрявшим в "In Progress" на середине перевода. При достижении
  очередь возвращает `paused`, и бот сообщает об этом один раз (не на каждый
  холостой опрос), пока причина не изменится.
- **Deny-list по путям** (`src/engine/guardrails.ts`) — миграции, `.env*`,
  конфиги CI, lock-файлы и файлы ключей/pem механически недостижимы для
  агента через собственный `--disallowedTools Edit(<glob>),Write(<glob>)` у
  Claude Code, подтверждено вживую: запрещённый путь отклоняется на уровне
  вызова инструмента (собственный ход агента сообщает, что не смог
  коснуться файла), а не просто не рекомендуется в промпте. Применяется к
  каждому вызову `run`/`queue` автоматически; отключить для отдельной задачи
  нельзя.

Лимиты на задачу (`MAX_ITERATIONS`, `MAX_BUDGET_USD`) и пропуск
неоднозначных `[backend]`/`[frontend]`/`[web]` тикетов из шага 2 — два других
гварда, уже работающих с более ранних шагов.

- **Секреты не попадают в окружение агента** (`buildAgentEnv()`,
  `src/engine/claudeEngine.ts`) — `child_process.spawn` по умолчанию
  наследует всё окружение родителя, а у агента на каждом ходу (implement,
  review, memory, testing-notes) есть Bash. Без этой защиты тикет с
  промпт-инъекцией вида "заодно выполни `curl ... -d \"$GITLAB_TOKEN\"`"
  сработал бы тривиально — токен уже лежал бы в его собственном окружении,
  файл трогать не нужно. `JIRA_PAT`/`GITLAB_TOKEN`/`TELEGRAM_BOT_TOKEN`
  явно вычищаются перед запуском `claude` (список — `SECRET_ENV_VARS` в
  `src/config.ts`, одна точка правды рядом с тем местом, где эти переменные
  читаются, чтобы новый секрет не забыли туда добавить). Не allowlist —
  собственный набор переменных окружения `claude` CLI (PATH, HOME, состояние
  логина) здесь не полностью известен, и allowlist рисковал бы незаметно
  сломать сам CLI; denylist бьёт точно по реальной угрозе, не трогая
  остальное.

- **Маскирование секретов в тексте роли** (`src/engine/secretScrub.ts`) —
  `buildAgentEnv()` закрывает только путь "агент читает секрет из своего же
  окружения". Остаётся другой: read-only роль (review/memory/testing-notes)
  читает файл, лог гейта или diff, где реальный секрет уже лежит (случайно
  закоммиченный токен, пример ключа в тестовой фикстуре), и копирует его
  прямо в свой текстовый ответ — а этот текст идёт в комментарий Jira,
  описание MR или коммитится в файл памяти проекта. `runClaudeTurn`
  (`claudeEngine.ts`) скрабит `resultText` перед возвратом, одной точкой для
  всех ролей сразу: сначала точные значения трёх настроенных секретов (по
  имени — `***cred:GITLAB_TOKEN***`, не просто звёздочки, чтобы не спутать с
  артефактом редактирования), затем жёсткие, редко ложно срабатывающие формы
  секретов, значения которых харнесс заранее не знает (Bearer-токен,
  PEM-блок, JWT, AWS access key id). Намеренно НЕ ловит общую прозу вида
  `password=` — она слишком легко ловит обычный текст ревью про
  переименование поля. Основано на двухслойном скрабе Avengers Harness
  (точные значения + эвристики формата).

- **Целостность гейтов** (`src/engine/gateIntegrity.ts`) — baseline-relative
  гейт можно обмануть: агент скипает ранее падавший тест вместо того, чтобы
  его чинить — количество ошибок честно падает, "не хуже, чем было"
  формально верно, а на деле ничего не исправлено. После каждого реального
  успеха механическая (без LLM) проверка сканирует дифф на: удалённый
  тестовый файл, свежедобавленный `.skip`/`.only`/`.todo`/`xdescribe`/`xit` в
  тестах, правку CI (`.gitlab-ci.yml`, `.github/workflows/*`) или конфига
  гейта (`jest.config.*`, `vitest.config.*`, `.eslintrc*`), правку скриптов
  `test`/`lint`/`build`/`typecheck` в `package.json`. Любое совпадение сразу
  уводит задачу в "нужен человек" — без повторной попытки: в отличие от
  обычного падения гейта, вторая попытка только рискует тем, что агент
  спрячет это аккуратнее. Переменная: `GATE_INTEGRITY_CHECK_ENABLED` (по
  умолчанию `true`) — лишнего хода модели эта проверка не стоит, выключать
  её имеет смысл разве что для отладки.

### Проверка: несколько гейтов вместо одной команды

Вместо единственной команды верификации (`yarn test`) на репозиторий можно
настроить несколько независимых гейтов — `typecheck`, `lint`, `test`,
`build` — каждый со своим baseline-сравнением (переменные
`*_GATE_TYPECHECK`/`*_GATE_LINT`/`*_GATE_BUILD` в `.env`, все опциональны).
Гейт, который был сломан ещё до правки агента, не блокирует его — сравнение
идёт со счётчиком ошибок/exit-кодом "до", а не с абсолютным требованием
"всё зелёное". При провале агент получает отдельную секцию фидбека по
каждому упавшему гейту, а не один общий текстовый блок — можно исправить
tsc+lint+test за одну итерацию, а не гоняться за каждым по очереди.

### Checkpoint: восстановление после сбоя

После каждой итерации цикл сохраняет механический checkpoint
(`.harness-state/checkpoints/<ISSUE-KEY>.json` — без коммита, без LLM) с
информацией о том, какой worktree/ветка/итерация сейчас в работе. Если
процесс бота упадёт посреди работы над тикетом (например, из-за нехватки
памяти), при следующем запуске бот найдёт осиротевший checkpoint и покажет
его как обычный "нужен человек" — с диффом и кнопками принять/отклонить —
вместо того чтобы молча потерять проделанную работу.

Раньше checkpoint удалялся в тот самый момент, когда цикл реализации
(`runCloseLoop`) возвращал результат — **до** push, открытия MR и перевода
тикета в Jira. Если процесс падал именно в этом окне, не оставалось вообще
никакой записи о задаче: ни checkpoint (уже удалён), ни "нужен человек" (ещё
не создан) — то самое "ledger побочных эффектов", о котором явно говорит
дизайн Avengers Harness, только применительно к нашей однопроцессной
архитектуре (без Postgres/lease — здесь не нужно, воркер один). Теперь
checkpoint живёт через push/MR/комментарий тоже и удаляется только тогда,
когда для задачи уже есть окончательная запись — либо `closed`, либо
durable `pendingHumanReview`. Честно: полностью герметично это всё равно не
сделать без транзакций — остаётся узкое окно между успешным переводом
статуса в Jira и локальной уборкой checkpoint/worktree, где свежий рестарт
покажет уже закрытую задачу как "нужен человек". Но это секунды, а не
полный push+MR+Jira-цикл, как было раньше.

### Уборка worktree после закрытия задачи

Раньше ни один путь (успех, принятое вручную "нужен человек") не удалял
worktree и локальную ветку после того, как MR уже открыт — они копились на
диске бесконечно. Теперь `cleanupWorktree()` вызывается ровно в тот
момент, когда задача действительно завершена: MR открыт, ветка запушена.
Удаление локального worktree/ветки ничего не теряет — `origin/<ветка>`, на
которой построен MR, никак не зависит от локального состояния репозитория
харнесса. Для `needs_human`-случаев worktree по-прежнему остаётся нетронутым
до решения человека — очистка срабатывает только после его реального
принятия или отклонения.

### Свежая база перед новой задачей

Симметрично уборке worктри выше, но на другом конце жизненного цикла задачи.
`git worktree add -B <branch>` без явной стартовой точки ветвится от текущего
локального HEAD основного чекаута репозитория (`BACKEND_REPO_PATH`/
`FRONTEND_REPO_PATH`) — а харнесс никогда сам не фетчит и не пуллит этот
чекаут. Если человек не зашёл руками и не сделал `git pull`, локальный HEAD
может отставать от `origin/<GITLAB_TARGET_BRANCH>` на день, неделю — сколько
угодно. Гейты, acceptance-тест и вся реализация в таком случае шли бы против
уже устаревшего кода, не того, во что реально вольётся итоговый MR.

`fetchFreshBase()` (`src/engine/git.ts`) делает `git fetch origin
<targetBranch>` и возвращает `origin/<targetBranch>` как startPoint для
`createWorktree` — ветка новой задачи начинается от того, что РЕАЛЬНО лежит
на целевой ветке прямо сейчас, а не от того, что последний раз кто-то
проверил себе на машину. Применяется только к по-настоящему новому worktree
(ни `resumeFrom.worktreeDir`, ни `existingWorktreeDir` не заданы) — у
worktree, который уже содержит незакоммиченную или закоммиченную работу,
подвинуть под ней базу — это уже задача про rebase с возможными
конфликтами, не про простой fetch; см. "Свежая база при резюме" ниже, где
именно это и реализовано отдельным механизмом.

Смоделировано по правилу Avengers Harness "ветка задачи ребейзится на
свежий dev перед гейтами" — но проще: у worktree с нуля ещё нет ни одного
собственного коммита, значит нечего реплеить и нечему конфликтовать, разница
только в том, от какого коммита начинать. Переменная: `FRESH_BASE_ENABLED`
(по умолчанию `true`).

### Детектор застревания

Цикл не всегда дожидается `MAX_ITERATIONS`, чтобы сдаться. После каждой
проваленной верификации харнесс считает "отпечаток" текущей ошибки — какие
гейты упали и первые несколько строк их вывода, с цифрами (номера строк,
счётчики) заменёнными на `#`, чтобы небольшой сдвиг номера строки не маскировал
"это та же самая ошибка" под "прогресс есть". Если отпечаток повторяется **два
раза подряд** — значит последняя правка агента вообще не изменила природу
проблемы — харнесс останавливается сразу с `stopReason: "stuck"`, не тратя
оставшиеся итерации и бюджет впустую.

Важно: если агент чинит одну ошибку и натыкается на другую (или чинит один из
нескольких упавших гейтов, а другой остаётся сломан тем же способом) —
отпечаток меняется, это не считается "застреванием". Срабатывает только на
буквальном топтании на месте. В Jira-комментарии и в карточке "нужен человек"
при этом явно названы гейты, где повторилась ошибка — не нужно самому
перечитывать сырой вывод, чтобы понять, на чём застряло.

### Бюджет контекста сессии

Цикл продолжает одну и ту же сессию `claude` через `--resume` на каждой
итерации (до `MAX_ITERATIONS`) — качество ответа начинает падать задолго
до реального лимита окна контекста. После каждого хода харнесс считает
настоящий размер контекста по формуле `input_tokens + cache_read_input_tokens
+ cache_creation_input_tokens` — не просто `input_tokens`: один ход может
показать `input_tokens: 2`, а реальный контекст при этом — под сто тысяч
токенов, почти всё из кэша. Если сумма превышает `CONTEXT_BUDGET_TOKENS` (по
умолчанию 150k, то же стартовое значение, что у Avengers Harness для той же
проверки), задача останавливается и уходит в "нужен человек" — так же, как
`max_iterations`/`max_budget`/`stuck`. Сам харнесс никогда не перезапускает
сессию автоматически — продолжать можно только явным кликом человека, см.
следующий раздел.

### «Продолжить» после остановки по лимиту контекста

У "нужен человек" от `context_budget` (и только от него — не от `stuck`/
`review_blocked`/других причин) есть третья кнопка в Telegram, рядом с
"Принять"/"Отклонить": **🔄 Продолжить (новая сессия)**. В отличие от
резюме брифа (тот же `claude --resume`, та же сессия, тот же контекст) —
здесь намеренно НЕ `--resume`: сессия, упёршаяся в лимит, уже деградировала
по качеству до того, как сработала сама проверка, продолжать именно её —
не чинить проблему, а длить её. Вместо этого — свежая сессия с нуля,
которой в первом же промпте честно показан текущий `git diff` worktree'а
(как есть, включая незакоммиченное) и исходные критерии приёмки.

Это осознанный компромисс, а не просто недостающая фича: свежая сессия не
помнит, что именно пробовала и почему не сработало предыдущая — она может
пойти по тому же пути, уже заведшему в тупик, или сделать что-то
несогласованное с уже написанным кодом. Именно поэтому это всегда ручной
клик, а не автоматический ретрай — человек явно соглашается на этот риск,
а не харнесс решает за него. Если и свежая сессия упрётся в тот же лимит —
кнопка появится снова, кликать можно сколько угодно раз.

Технически: `CloseLoopResumeState.freshSession` — третий флаг-переключатель
поведения резюме (наряду с обычным "та же сессия" и `reviewResume`),
обнуляет `resumeSessionId` вместо `--resume`'а старой сессии, и отдельно
обнуляет `iteration`/`previousFingerprint` резюме — новая сессия получает
свой собственный полный лимит `MAX_ITERATIONS`, а не остаток от старой, и
не может быть ошибочно признана "залипшей" на первом же ходу просто
потому, что застала тот же ещё-не-исправленный гейт, что и предыдущая.
Пока работает только для одиночных (не кросс-репо) задач — для кросс-репо
бэкенд/фронтенд-половин кнопка намеренно не показывается, см. комментарии
на обоих `setPendingHumanReview` в `queue.ts`.

### Неверный тег репозитория — не стоппер

Тег `[backend]`/`[frontend]`/`[web]` определяет, какой репозиторий вообще
будут читать на шаге propose — но тег ставит человек при заведении тикета,
и иногда ошибается: симптом описан как "права в UI", тег стоит
`[frontend]`, а по факту единственная дыра — в бэкенде, который вообще не
проверяет право на сервере (реальный случай, XEN-541). До этой фичи
propose-ход в такой ситуации читал код фронтенда, не находил там ничего
менять, и в лучшем случае формулировал критерии вида "задокументировать и
передать бэкенду" — тикет формально обрабатывался, но ни строчки кода не
менялось.

Теперь proposeSolution прямо говорит модели: решишь, что фикс целиком в
другом репозитории — не пиши план, ответь одной строкой `РЕПОЗИТОРИЙ:
backend` (или `frontend`). Если такая строка пришла и названный репозиторий
отличается от того, что сейчас читается, харнесс:

1. Переписывает тег в заголовке Jira-тикета (`retagTitle` в `mapToTask.ts`
   снимает все существующие теги и ставит один правильный — через
   `JiraClient.updateSummary`), чтобы и человек, глядя на тикет, видел
   актуальный репозиторий, а не старую ошибку заведения.
2. Оставляет комментарий в Jira с объяснением, что и почему поменялось.
3. Запускает propose заново — уже против правильного репозитория — и
   использует этот, второй, результат как итоговое предложение.

Критично: `PendingApproval.title` обновляется на отретегированный, а не
просто заголовок в Jira — `confirmPending()` на подтверждении пересобирает
`JiraIssue` именно из `pending.title` (не свежим запросом в Jira), и
`dispatchIssue()` там заново гоняет `detectRepo()`. Если бы отретегировали
только в Jira, а `pending.title` остался старым, подтверждение всё равно
укатилось бы в исходный (неправильный) репозиторий.

Ограничено одним перенаправлением за propose — если и второй репозиторий
тоже ответит "РЕПОЗИТОРИЙ: ...", харнесс не будет пинг-понговать между
ними, а просто возьмёт то, что вернул второй ход (пусть даже план
окажется пустым — лучше честно пустой план, чем бесконечный цикл
ре-анализа). Опция `REPO_RETAG_ENABLED` (по умолчанию включена) выключает
это целиком: без неё propose-ход никогда не получает инструкцию про
`РЕПОЗИТОРИЙ:` и ведёт себя ровно как раньше. Относится только к обычным
(не кросс-репо) тикетам — `proposeCrossRepoSolution` всегда анализирует
оба репозитория по отдельности, там "не тот репозиторий" не имеет смысла.

### Независимое ревью: что не ловят гейты

Прохождение всех гейтов (typecheck/lint/build/тесты/acceptance) не значит, что
с кодом всё в порядке — оно значит только то, что проверено *механически*.
После каждого реального успеха (гейты прошли, коммит сделан) отдельный ход на
Opus читает весь дифф и ищет то, что автоматика структурно не способна
поймать: уязвимости, архитектурные проблемы, граничные случаи без покрытия,
нарушение конвенций проекта. Ревьюеру явно сказано не повторять то, что уже
гарантировано тестами/типами, и не придираться к стилю, если он совпадает с
остальным проектом.

Находки делятся на два типа:
- **Блокирующие** — не идут сразу к человеку. Реальный диалог: находки
  уходят в ту же сессию `implement`'а (`resumeSessionId`, он помнит всё, что
  уже делал) как задание на фикс, гейты прогоняются заново, ревьюер смотрит
  снова — цикл "ревьюер ↔ разработчик", а не одноразовая проверка. Капается
  `MAX_REVIEW_ROUNDS` раундами (по умолчанию 3) — два агента, которые не
  сходятся, не должны спорить до бесконечности на весь бюджет задачи; если
  за отведённые раунды ревьюер так и не доволен, тогда уже уходит в
  существующий флоу "нужен человек" — с диффом, историей раундов в причине,
  кнопками принять/отклонить.
- **Замечания** — не блокируют ничего, едут в описание MR как есть, чтобы
  ревьюер-человек их видел, не перезапуская ревью заново.

Каждый раунд пишется на диск отдельно — `.harness-state/tasks/<ISSUE-KEY>/
reviewer/round-N.md` (что нашёл ревьюер) и `dev/round-N-response.md` (что
ответил/исправил разработчик) — так человек, которому в итоге эскалировали
задачу, видит настоящую переписку по раундам, а не только финальный вердикт.

Живой пример (прогнано вживую, не выдумано): дифф с
`SELECT ... WHERE name = '${name}'` — типы и сборка такое пропускают
(строка валидна с точки зрения TS), а ревью поймало SQL-инъекцию как
блокирующую находку с конкретным фиксом (параметризованный запрос) и даже
нюансом про multi-statement в `pg`.

Переменные: `REVIEW_MODEL` (по умолчанию Fable 5.1 — тот же уровень
возможностей, что у `implement` (Opus), но намеренно **другая модель**, не
просто более дешёвая: ревьюер, устроенный так же, как разработчик, скорее
разделит его слепые пятна, а не только сильные стороны — то же рассуждение,
по которому у ЕТС Тендер ревью намеренно идёт другой моделью, не той же, что
у разработчика), `MAX_REVIEW_ROUNDS` (по умолчанию `3`), общий выключатель
`REVIEW_ENABLED` (по умолчанию `true`).

### Брифы: вопрос вместо угадывания

Смоделировано напрямую по образцу боевых "брифов" ЕТС Тендер (10-15 в день,
ответ одним кликом): разработчику в промпт добавлена явная инструкция — если
что-то в задаче по-настоящему неоднозначно (требование можно понять двумя
способами, решение с реальными последствиями, в которых агент не уверен) —
не угадывать и не продолжать, а остановиться и ответить строго заданным
форматом (`БРИФ` / `ВОПРОС:` / `ВАРИАНТЫ:` / `РЕКОМЕНДАЦИЯ:` / `ПОЧЕМУ:`).
Харнесс парсит это, ставит задачу на паузу и присылает в Telegram вопрос с
кнопками — по одной на вариант, рекомендация агента помечена ★.

Технически самое нетривиальное здесь — не парсинг, а то, что цикл реализации
должен уметь по-настоящему **приостановиться и продолжиться** с места
остановки, а не начать заново: `runCloseLoop` сохраняет вместе с паузой то,
что нельзя пересчитать заново (ID сессии `claude`, уже установленные gates/
baselines, путь к acceptance-тесту) — иначе продолжение заново переустановило
бы baseline по worktree, в котором уже есть частичная работа, что было бы
попросту неверно. Когда человек жмёт кнопку, харнесс резюмирует **ту же самую
сессию** `claude` (`--resume`) с ответом в промпте — агент помнит весь
контекст задачи, ему нужно передать только ответ, не пересказывать всё заново.

**Баг, который был здесь до недавнего времени (найден и исправлен не вживую
на бою, а при разборе самого механизма резюмирования):** в этом списке того,
"что нельзя пересчитать заново", не хватало самого важного — пути к
worktree. Без него `runCloseLoop` на резюме падал в тот же код, что и для
новой задачи: `createWorktree()`, который форсированно удаляет и
пересоздаёт worktree, если он уже зарегистрирован (логика рассчитана на
"прошлый прогон упал/заброшен" — осмысленно для восстановления после
крэша, разрушительно для живой паузы). На практике это значило: любой
брифинг (в основном ходу, в раунде ревью, в любой половине кросс-репо
задачи) при резюме **тихо стирал** всю незакоммиченную работу предыдущих
итераций перед тем, как продолженная сессия `claude` вообще успевала её
увидеть — сессия своим контекстом помнит правки, которых на диске уже нет.
Подтверждено вживую (`git worktree remove --force` на worktree с
незакоммиченными правками реально их удаляет, не просто снимает
регистрацию). Теперь `worktreeDir` — обязательное поле
`CloseLoopResumeState`, и резюме сначала проверяет его, прежде чем вообще
думать про `createWorktree()`.

Каждый раунд (вопрос → ответ) записывается в
`.harness-state/tasks/<ISSUE-KEY>/` — так же, как раунды ревью.

#### Свежая база при резюме, не только при старте

`fetchFreshBase` (см. выше) закрывает только "worktree новой задачи
ветвится от свежего dev" — ровно один раз, в момент создания. Пауза на
бриф может длиться часы или дни, пока человек не ответит, и всё это время
`dev` продолжает жить своей жизнью. Раз worktree теперь честно переживает
паузу (см. баг выше), встаёт настоящий вопрос: насколько он успел устареть
к моменту, когда человек наконец отвечает?

`rebaseOntoFreshBase()` (`src/engine/git.ts`) решает именно это — вызывается
один раз, прямо при входе в `runCloseLoop` на резюме (любом из трёх видов),
до того как продолженная сессия `claude` вообще получит ответ человека:
фетчит `origin/<targetBranch>` и перебазирует текущую ветку worktree на него
с `--autostash` (незакоммиченные правки от итераций до паузы — обычный
случай сразу после брифа — переживают ребейз тем же образом, что и
закоммиченные).

Конфликт — не повод для ещё одной попытки вслепую: ребейз откатывается
(`git rebase --abort`, worktree возвращается ровно в то состояние, что было
до вызова) и задача сразу уходит в "нужен человек" с сырым выводом `git`
в причине — то же рассуждение, что у блока, который останавливается, когда
раунд ревью ломает гейт: у человека больше контекста, чтобы разрешить
настоящий конфликт, чем у ещё одной слепой попытки. Смоделировано на
правиле Avengers Harness "конфликт → BLOCKED человеку", применённом здесь
не к старту задачи (там ребейзить нечего — ни одного собственного коммита),
а к её возобновлению.

**Сознательно не доделано (а не забыто):** если ребейз реально подвинул
HEAD (`rebaseOntoFreshBase()` возвращает `rebased: true`), gate baseline,
установленный ДО паузы, не пересчитывается — только логируется.
Пересчитать честно значило бы прогнать гейты против чистого
`origin/<target>` без собственных коммитов/незакоммиченного задачи — но
ребейзнутый worktree их уже смешал (autostash возвращает незакоммиченное
обратно СРАЗУ после ребейза), так что наивный повторный
`establishBaselines()` прямо в этом worktree подмешал бы собственные правки
агента в "baseline существующего шума". Корректно — одноразовый disposable
worktree только для замера; не сделано, потому что эффект (небольшой сдвиг
счётчика падающих тестов/lint от чужих, не относящихся к задаче коммитов
dev) низкой серьёзности и вероятности относительно стоимости лишнего
полного прогона гейтов на каждом resume, где dev успел продвинуться.

#### Брифы в раунде правки по замечаниям ревью

Изначально работали только в основном ходу реализации — раунд правки по
замечаниям ревью (см. "Независимое ревью" ниже) брифов не поддерживал: кроме
ID сессии/gates/baselines нужно было ещё восстановить "на каком раунде ревью
мы остановились", и без этого прервавшийся на вопрос fix-ход просто завис бы
без шанса вернуться к обычному потоку.

`runCloseLoop` разделён на две части: основной цикл реализации и
`runPostImplementSuccess` — всё, что идёт после успешного коммита (проверка
целостности гейтов, цикл ревью↔правка, инструкция тестировщику, память).
Вторая часть вызывается и с нуля (обычный успех), и напрямую при
возобновлении — тогда `CloseLoopResumeState.reviewResume` несёт номер раунда
и список блокирующих находок, на которые отвечал fix-ход, когда поднял брифа.
Возобновление не перезапускает `reviewChanges` (дифф не менялся с момента
вопроса — незачем ревьюить второй раз одно и то же), а продолжает ИМЕННО тот
fix-ход с ответом человека, и уже после него — обычный цикл ревью с
следующего раунда. Та же инфраструктура паузы/резюме (`PendingBrief`,
`resolveBrief`) работает без изменений: ей всё равно, в какой момент цикла
возник `CloseLoopResumeState`.

**Баг, найденный при повторном аудите этого же механизма** (не вживую на
бою — при разборе, что именно означает "конфиг поменялся, пока бриф висел"):
бриф на паузе может пережить перезапуск бота — `PendingBrief` персистится
на диск. Если между паузой и резюме `.env` поправили (`REVIEW_ENABLED` →
`false`, или `MAX_REVIEW_ROUNDS` понизили ниже номера раунда, на котором
стоял бриф) и бот перезапустили — наивное продолжение просто пропустило бы
весь блок ревью (`if (config.review) {...}` ложно, или диапазон цикла `for`
пустой с самого начала) и отрапортовало задачу как `verified`, полностью
проигнорировав уже данный человеком ответ на блокирующую находку.
`reviewResumeNowUnsafe()` (`loop.ts`) ловит оба случая заранее и эскалирует
через существующий `review_blocked` → "нужен человек" с теми же находками,
вместо ложного "всё чисто".

#### Брифы в кросс-репо задачах

Раньше вопрос от бэкенда или фронтенда уходил через флоу "нужен человек"
текстом, а не кнопками — не терялось, просто не one-click. Теперь брифы из
обеих половин кросс-репо задачи — такие же кнопки, как и в одиночном
репозитории: `CrossRepoBriefContext` (`types.ts`) привязан к `PendingBrief` и
несёт ровно то, чего не хватает, чтобы продолжить автономный хэндофф после
ответа человека —
- на брифе от бэкенда: задачу/ветку/репозиторий фронтенда, чтобы после
  успешного резюме бэкенда реализация фронтенда началась автоматически, как
  и при обычном (без брифа) прохождении;
- на брифе от фронтенда: MR бэкенда, его стоимость/инструкцию тестировщику/
  число раундов ревью — собственный worktree бэкенда к этому моменту уже
  убран, и это единственное, что нужно для финального объединённого
  комментария в Jira.

`afterBackendAttempt`/`afterFrontendAttempt` (`queue.ts`) — общие продолжения
для первой попытки и резюмирования после брифа, тот же принцип, что
`handleCloseLoopOutcome` для одиночного репозитория: не важно, первая это
попытка или возобновлённая, дальнейшая логика (брифа/ошибка/успех → хэндофф
или финальный комментарий) одна и та же.

### Оценка стоимости/времени до подтверждения

Раньше предложение в Telegram показывало только стоимость самого анализа
(`propose`) — сколько будет стоить и сколько времени займёт реализация,
было неизвестно до того, как она уже произошла. Теперь к каждому
предложению добавляется вторая строка: медианные $ и минуты по истории уже
закрытых задач (`.harness-state/bot-state.json`), либо "недостаточно
истории для прогноза", если данных ещё нет.

Логика в `estimateCost()` (`src/bot/state.ts`):
- в выборку идут только `closed` и `needs_human` (реальная работа была
  сделана) с `costUsd > 0` — `skipped` (не удалось определить репозиторий,
  отменено человеком) ничего не стоил и не отражает реальную задачу;
- если для целевого репозитория накопилось хотя бы 3 такие записи — оценка
  считается только по нему (XEN-похожая задача в `front-ai` не похожа по
  стоимости на задачу в `back-ai`); иначе — откатывается на всю историю;
- `durationMs` есть не у всех записей (поле появилось позже, старые записи
  в `bot-state.json` его не имеют) — такие записи всё равно участвуют в
  оценке стоимости, просто не участвуют в оценке времени, а не выбивают
  отображение "0 минут".

Это прогноз по прошлым задачам, не предсказание для конкретной — задача
с неожиданно широким диффом может стоить сильно больше медианы.

### Метрики по истории

`estimateCost()` выше отвечает на вопрос "сколько обычно стоит задача,
прежде чем её одобрить" — `computeMetrics()` (тот же `src/bot/state.ts`)
отвечает на другой: "как харнесс вообще справляется", команда `/metrics`.
Отличия от `estimateCost()` намеренные:
- считается по ВСЕЙ истории, без отката на меньшую выборку — это трек-рекорд,
  а не прогноз, его не нужно "доверять только при достаточной выборке";
- `closed` и `needs_human` входят оба (а не только `costUsd > 0`) — доля
  эскалации должна учитывать и мгновенные needs_human (например, не настроен
  `GITLAB_TOKEN`), не только дорогие;
- среднее число раундов ревью считается ТОЛЬКО по `closed` — у
  `needs_human`-эскалации из цикла ревьюер↔разработчик уже есть свой явный
  `stopReason: "review_blocked"` в причине, мешать её раунды со "ревью
  согласовало фикс за N раундов" было бы вводящим в заблуждение усреднением
  двух разных исходов.

`reviewRounds` проброшен через весь путь от `CloseLoopResult` до
`TaskRecord` отдельной (небольшой, чисто wiring) правкой — раньше нигде не
сохранялся. Для кросс-репо задачи (`sumReviewRounds()` в `queue.ts`) —
сумма раундов бэкенда и фронтенда, `undefined` только если ревью не бежало
ни для одной из половин (единый `REVIEW_ENABLED` на обе).

Свободный текст роутится в `/metrics` так же, как в `/status`/`/budget` —
через `classifyMessage`, без права модели придумать цифры самой.

### Кросс-репо задачи: бэкенд → фронтенд автономно

Раньше тикет с обоими префиксами (`[backend]` и `[frontend]`/`[web]` сразу)
`detectRepo()` помечал как `ambiguous`, и дальше бот просто писал в Jira
"нужен человек" и ничего не делал. Теперь это реальный, автономный путь:

1. **Одно подтверждение на весь тикет.** `propose` запускает анализ дважды —
   отдельно по `back-ai` и по `front-ai` (каждый видит только свой код, так
   своя часть плана и критериев естественно получается про свой репозиторий,
   без выдумывания общего словаря). В Telegram человек видит оба плана и оба
   набора критериев сразу, одной кнопкой — как у обычной задачи.
2. **Бэкенд реализуется первым.** После подтверждения бот доводит бэкенд-часть
   до реального MR (тот же `runCloseLoop`, те же гейты/acceptance-тест/ревью,
   что и у одиночной задачи).
3. **Фронтенд получает настоящий дифф бэкенда как контекст**, а не только
   текст тикета — агент ориентируется на реальные эндпоинты/DTO, а не
   угадывает их по описанию.
4. **Дальше — без паузы на человека.** Хэндофф бэкенд → фронтенд полностью
   автономный (сознательный выбор — то же доверие, что и у остального
   пайплайна: гейты и ревью уже стоят на страже обеих частей).
5. **Частичный успех не теряется.** Если бэкенд не закрылся — фронтенд даже
   не запускается (не на чем писать код). Если бэкенд закрылся, а фронтенд
   застрял — бэкендовский MR остаётся открытым сам по себе, а "нужен человек"
   встаёт только за фронтенд, со ссылкой на уже готовый MR бэкенда.
6. **Тикет переходит на ревью только когда закрыты обе половины** — с одним
   комментарием в Jira, перечисляющим оба MR.

Намеренно не потребовалось отдельной message-bus инфраструктуры (вроде
внутреннего Mercury/pg-boss) — весь хэндофф живёт внутри одного процесса
(`runCrossRepoJob` в `src/queue.ts`), это просто последовательный вызов
`runCloseLoop` дважды с передачей контекста между вызовами, а не
независимые сервисы, которым нужна устойчивая асинхронная шина.

Если любая из половин поднимает брифа вместо того, чтобы гадать — это тоже
one-click, не "нужен человек" текстом; см. "Брифы в кросс-репо задачах" выше.

### Инструкция для тестировщика: автоматически, в комментарии Jira

До этого MR открывался, а то, как именно проверить, что фикс/фича реально
работают, тестировщик додумывал сам — читая тикет и сам MR. Теперь, сразу
после того как гейты прошли и ревью не нашло блокирующих проблем, ещё один
read-only ход (Sonnet, `src/engine/testingNotes.ts`) смотрит на задачу,
критерии приёмки и реальный дифф и пишет инструкцию в том же формате, что
команда уже использует для ручных багрепортов:

```
ПРЕДУСЛОВИЯ:
...
ШАГИ:
1. ...
ОЖИДАЕМЫЙ РЕЗУЛЬТАТ:
...
```

Модели явно сказано не ссылаться на файлы/функции/код — тестировщик
проверяет поведение приложения (экраны, кнопки, эндпоинты), а не читает
дифф. Результат попадает прямо в тот же комментарий в Jira, что и ссылка на
MR, под заголовком "Как тестировать:" — не нужно искать отдельно.

Для кросс-репо задач (см. выше) в один и тот же финальный комментарий
попадают обе инструкции — "Бэкенд:" (как проверить через API) и
"Фронтенд:" (как проверить через UI) — вместе они описывают, как
протестировать фичу целиком.

Это чисто информационный шаг — в отличие от независимого ревью, он никогда
не блокирует пуш: если ход упал с ошибкой или вернул пустой текст, задача
всё равно закрывается, просто без инструкции в комментарии. Переменные:
`TESTING_MODEL` (по умолчанию Sonnet — тот же уровень, что у propose/memory,
это не открытый цикл, а один ограниченный ход), общий выключатель
`TESTING_NOTES_ENABLED` (по умолчанию `true`).

### Докладчик с отчётом: сводка для заказчика тикета, в Telegram

До этого закрытая задача в Telegram выглядела одной строкой: "✅ Готово:
XEN-55 закрыт, MR — ..., потратил $0.42" — ни слова о том, что вообще
произошло. Полезно для разработчика, бесполезно для того, кто поставил
задачу и код не читает. Инструкция для тестировщика выше тоже не подходит
для этой аудитории — она про ШАГИ ПРОВЕРКИ (кнопки, экраны), а не про смысл
изменения, и уходит в Jira, а не в Telegram.

Отдельный read-only ход (Sonnet, `src/engine/closeReport.ts`), сразу после
инструкции тестировщику, получает задачу и реальный дифф и пишет 2-4
предложения простым языком: какую проблему решали и что изменилось для
пользователей или бизнеса. Явно сказано не упоминать файлы, функции,
классы, библиотеки, эндпоинты — рассказать так, как объяснил бы коллеге без
техфона. Результат добавляется отдельным абзацем к закрывающему сообщению в
Telegram, не в комментарий Jira (та аудитория — тестировщик/разработчик, не
тот, кто поставил задачу).

Для кросс-репо задач сводки обеих половин склеиваются в одну (та же логика,
что у инструкции тестировщика). Чисто информационный шаг, как и инструкция
тестировщику — ошибка хода или пустой ответ не блокируют закрытие задачи,
просто сообщение останется коротким, как раньше. Переменные: `REPORT_MODEL`
(по умолчанию Sonnet, тот же уровень, что у testing/memory/propose — это не
открытый цикл, а один ограниченный ход), общий выключатель
`CLOSE_REPORT_ENABLED` (по умолчанию `true`).

**Сознательно не реализовано (а не забыто):** скриншоты для фронтенд-тикетов
— требуют Playwright (новая тяжёлая зависимость в проекте, которой сейчас
нет вообще, браузерная автоматизация) и ответа на вопрос "с какого стенда
снимать" (харнесс сейчас не знает ни реального URL задеплоенного стенда, ни
доступов к нему — работает только с git-репозиторием). Текстовая часть —
независимая, законченная фича сама по себе; скриншоты, если понадобятся
позже — отдельное расширение этой же роли, не переделка.

### Текстовый отчёт вложением в Jira: для тестировщика, без дополнительного хода

Докладчик выше и инструкция тестировщику (см. ниже "Независимое ревью" →
соседний раздел) пишут две половины одного и того же: "что изменилось" и
"как это проверить" — но обе живут только в тексте (Telegram-сообщение и
комментарий в Jira соответственно), и тестировщику приходится либо листать
переписку, либо просить переслать. `src/engine/workReport.ts` —
чистая функция `buildWorkReportDocument()`, которая СКЛЕИВАЕТ уже
сгенерированные `closeReport`/`testingNotes` в один читаемый текстовый
документ ("Что сделано: ... Как проверить: ...") БЕЗ дополнительного хода
`claude` — обе части уже посчитаны и оплачены на предыдущих шагах, это
чистая композиция строк.

Прикрепляется через `JiraClient.addAttachment()` (multipart upload,
`X-Atlassian-Token: no-check` — отдельный от Bearer auth XSRF-чек Jira)
ровно в момент перехода тикета из "В работе" дальше — то есть и при обычном
автоматическом закрытии, и при ручном принятии "нужен человек" человеком
через кнопку ✅ в Telegram (`resolveHumanReview`). Для второго случая
`testingNotes`/`closeReport` раньше вообще не генерировались (human-accept
не проходит через `runCloseLoop`) — теперь `generateAndAttachWorkReport()`
прогоняет те же два read-only хода прямо там, на уже закоммиченном
worktree, и только после этого прикрепляет файл. Для этого `PendingHumanReview`
и сам `Checkpoint` (на случай восстановления после краша) теперь несут
`description`/`acceptanceCriteria` задачи — раньше там была только `title`,
которой не хватает для осмысленного промпта.

Полностью опционально и никогда не блокирует закрытие/принятие задачи:
ошибка генерации или загрузки вложения — это `appendLog`-предупреждение, не
исключение. Переменная: `WORK_REPORT_ENABLED` (по умолчанию `true`) — не
зависит от `CLOSE_REPORT_ENABLED`/`TESTING_NOTES_ENABLED` напрямую, но
документ просто не появится, если обе исходные части выключены или
вернулись пустыми.

### Мини eval-набор: сравнение до/после смены промпта или модели

Без этого менять `IMPLEMENT_MODEL`, промпт `propose` или формат acceptance-теста
приходится вслепую — "вроде стало лучше" не проверить. `node dist/cli.js eval`
прогоняет харнесс (ровно тот же `runCloseLoop`, что и в проде, без моков) против
нескольких **реальных, уже закрытых** багов из `back-ai`/`front-ai`.

Как устроен кейс (`evals/cases/<id>.json`): `baseCommit` — состояние репозитория
прямо до настоящего фикса, `referenceCommit` — сам фикс, `hiddenTestPaths` —
тестовые файлы из этого фикса. Запуск кейса:

1. Создаётся worktree на `baseCommit` (а не HEAD) — агент видит баг таким,
   каким он был на самом деле, без доступа к будущей истории (нет `git fetch`,
   агенту и так недоступен Bash).
2. Из `referenceCommit` восстанавливается **настоящий исторический тест** —
   это и есть скрытый критерий приёмки, фиксированный и воспроизводимый
   (в отличие от прод-пайплайна, где тест каждый раз генерируется заново —
   для сравнения двух прогонов eval нужна постоянная, а не плавающая метрика).
3. Гейты для eval — не весь обычный набор репозитория: полный `test` (весь
   regression-сьют) намеренно исключён — на этой машине он дважды уронил
   OOM-killer за сессию, а eval-кейсы должны быть дешёвыми и безопасными,
   чтобы их гоняли часто. Остаются только `typecheck`/`build` (если настроены)
   и сам скрытый тест как строгий гейт.
4. Дальше — обычный `runCloseLoop`: агент видит фидбек от упавшего скрытого
   теста как от любого другого гейта, итерирует, детектор застревания и
   лимиты бюджета работают как в проде.

```bash
node dist/cli.js eval                       # все кейсы, модель из .env, k=1
node dist/cli.js eval --case XEN-364        # один кейс
node dist/cli.js eval --model claude-sonnet-5  # сравнить модель, не трогая .env
node dist/cli.js eval --k 3                 # каждый кейс 3 раза — pass@1/pass^3
```

Результат — таблица по каждому кейсу (pass/fail, стоимость, итерации, какие
гейты упали) плюс итоговый pass rate, и сохраняется в
`.harness-state/eval-runs/<timestamp>.json` для сравнения прогонов между собой.

Сейчас в наборе 3 кейса (XEN-364 — видимость документов в Общей папке,
XEN-369 — IDOR в приглашениях, XEN-302 — отсутствие проверки прав на теги) —
намеренно мини: каждый добавленный кейс стоит реальных денег на каждый прогон,
расширять набор стоит по мере накопления показательных регрессий, а не
заранее.

#### `--k`: pass@1 против pass^k, а не один прогон на кейс

Агент недетерминирован — один прогон на кейс (`k=1`, как было раньше)
отвечает только на вопрос "прошёл ли этот конкретный прогон", а не "насколько
надёжно харнесс решает этот класс багов". `EvalCaseAggregate`
(`src/evals/types.ts`) группирует `k` попыток одного кейса и считает две
разные вещи:
- **pass@1** — средняя доля успешных попыток (2 из 3 прошли → `0.67`);
- **pass^k** — прошли ли ВСЕ `k` попыток. Строже, чем pass@1, и это та
  цифра, что реально важна для харнесса, рассчитанного на работу без
  присмотра: "проходит примерно 2 раза из 3" на практике означает, что
  примерно каждый третий прогон на реальном тикете потребует человека —
  это прячется внутри среднего, но не внутри pass^k. Та же терминология и
  рассуждение, что в eval-дизайне Avengers Harness.

При `k=1` (дефолт) отчёт и итоговый код выхода выглядят ровно как раньше —
это чистое расширение, не смена поведения по умолчанию. При `k>1` строка
кейса в отчёте показывает агрегат (`N/k`, суммарная стоимость, `pass@1=`),
а каждая попытка остаётся под ней отдельной строкой — расследовать, какая
именно попытка сломалась и на чём, можно не перезапуская прогон.

Дороже дешёвого: `k=3` на 3 кейсах — это 9 полных прогонов `runCloseLoop`,
реальные деньги за каждый. Решение по гипотезе (сменить модель/промпт)
стоит принимать по парному сравнению pass^k между baseline и вариантом на
одинаковом `k`, а не по разнице в доли процента на одном прогоне каждого —
на 3 кейсах один кейс весит слишком много, чтобы мелкая разница значила
что-то, кроме шума.

### Автополлинг в `bot.ts`: закрыт обход подтверждения в `queue`/дашборде

Полный аудит проекта нашёл главный пробел в собственной границе
автономности харнесса: `queue` CLI (исторически рекомендованный в HANDOFF.md
под cron/watch) и кнопка "Запустить" в дашборде оба вызывали
`dispatchIssue()` напрямую — весь цикл закрытия задачи (реализация → ревью →
push → MR → перевод тикета на ревью) без единого шага подтверждения
человеком. Тот же самый `pendingApproval`/"✅ Подтвердить" в Telegram,
который существует именно для этого, был одним кликом/одним cron-тиком
обходим полностью.

Исправление — архитектурное, не точечный патч одной функции:

- **`queue.ts`**: `dispatchIssue()` теперь требует `acceptanceCriteria` (не
  опциональный параметр с дефолтом `[]`) и достижим только из
  `confirmPending()` — единственного места, где approval уже реально
  получен. И `proposeNext()`, и `proposeIssueByKey()`, и сам `dispatchIssue()`
  гейтятся общей `hasUnresolvedWork()` — задача не стартует, пока
  `currentJob`/`pendingApproval`/`pendingHumanReview`/`pendingBrief` ещё
  не разрешены (раньше `pendingBrief` вообще нигде не проверялся — пауза на
  бриф по одному тикету не мешала начать второй). `runQueueOnce()`
  переписан в однострочный вызов `proposeNext()` — `queue` теперь только
  предлагает, как и всё остальное; бывшая `runTicketByKey()` (прямой dispatch
  для дашборда) удалена целиком.
- **`web/server.ts`**: `/api/tickets/:key/start` теперь вызывает
  `proposeIssueByKey()`, а не `runTicketByKey()`. `startDashboardServer`
  принимает опциональный `onProposal` колбэк — когда дашборд встроен в
  процесс `bot`, найденное предложение сразу уходит в Telegram с теми же
  кнопками ✅/❌; у самостоятельной `dashboard`-команды колбэка нет (бот не
  запущен — послать уведомление некуда), но предложение всё равно
  фиксируется в `pendingApproval` и видно через `/status` после запуска бота.
- **`bot.ts`**: вместо `queue` на cron — сам `bot`, пока запущен (`/start`
  или свободный текст "покажи список"), поллит Jira через уже готовый
  `proposeNext()` на таймере: `ACTIVE_POLL_SECONDS` (по умолчанию 10с) сразу
  после пропущенного тикета (следующий может быть тут же), `IDLE_POLL_SECONDS`
  (по умолчанию 300с) после пустой очереди или пока слот занят чем-то, что
  ждёт решения человека — нет смысла долбить Jira, пока approval/ревью/бриф
  уже показаны со своими кнопками. `/stop`/`/kill` останавливают таймер
  (`clearPoll()`), а не только отключают кнопки уже показанных списков — до
  этой правки `/stop` не переживал завершение текущей задачи (см. ниже).
  Найденное предложение показывается тем же `announceProposal()`, что и
  восстановление `pendingApproval` после рестарта — раньше это был
  задублированный инлайн-код в двух местах.
- **Попутно найденный и исправленный баг**: `sendTicketMenu` — функция,
  которая и рисует список тикетов по `/start`, и автоматически зовётся
  после каждого закрытия задачи, чтобы очередь продолжалась без ручного
  `/start` — безусловно выставляла `state.running = true`. Нажатие `/stop`
  посреди выполняющейся задачи молча отменялось в момент, когда эта задача
  закрывалась. Теперь `sendTicketMenu` принимает `{ resume: true }` только
  от явных действий пользователя (`/start`, intent "список"); авто-вызов
  после закрытия задачи уважает уже выставленный `false`.

### Шаг 7: тесты, и механический гейт, который их требует

`npm test` запускает набор через встроенный тест-раннер Node (`node:test`,
Node 20+), загружаемый через `tsx` — без лишней зависимости на фреймворк
тестирования. Покрывает роутинг `detectRepo`/`toTaskSpec`, форматирование
промптов, логику baseline-сравнения гейтов из движка верификации шага 6,
реальные интеграционные тесты на временных git-репозиториях для создания
worktree/коммита/диффа, и запись/восстановление checkpoint.

Новые функции должны поставляться с тестами в том же изменении — это
требование проверяется механически, а не держится на памяти, через два
git-хука в `.githooks/`:

- **`pre-commit`**: прогоняет весь набор тестов; упавший тест блокирует
  коммит целиком.
- **`commit-msg`**: блокирует коммит, который трогает логику в
  `src/**/*.ts`, но не затрагивает ни один `*.test.ts` файл — если только в
  сообщении коммита нет явной строки `No-Test: <причина>` (для коммитов,
  которым тест действительно не нужен: документация, конфиги, чистый
  монтаж). Это предусмотренный способ пропустить проверку для конкретного
  коммита — не `git commit --no-verify`, который заодно пропустил бы и
  проверку тестов выше.

Эти хуки не включены по умолчанию на свежем клоне (`.git/hooks` не
версионируется) — один раз укажите git на отслеживаемую директорию:

```
git config core.hooksPath .githooks
```
