# jira-harness — передача проекта

Этот файл — брифинг для агента/разработчика, который берёт на себя **полное
владение** этим проектом: дальнейшую разработку, баг-фиксы, принятие решений
по архитектуре. Он написан так, чтобы можно было понять всё необходимое, не
перечитывая всю историю коммитов.

**Порядок чтения:** сначала этот файл целиком, потом `README.md` (подробное
техническое описание каждой фичи, с обоснованием "почему так", а не только
"что"). Этот файл — карта и контекст; README — источник истины по деталям
реализации. Если они противоречат друг другу — верь коду, потом README,
потом этому файлу (он может немного отставать от самых свежих изменений).

---

## 1. Что это за проект, одним абзацем

`jira-harness` — бот, который берёт тикеты из Jira, самостоятельно читает
код, пишет фикс, прогоняет тесты/линтер/тайпчек, при необходимости повторяет
попытки с учётом ошибок, независимый ревьюер проверяет дифф, и в конце
открывает Merge Request в GitLab, переводя тикет в статус ревью. Управляется
через Telegram-бота (персонаж "Зам. CEO") — слэш-командами и свободным
текстом — с живым веб-дашбордом для наблюдения. Жёсткая граница автономности:
бот доходит до открытия MR и перевода тикета на ревью — **никогда не мержит
сам и никогда не закрывает тикет**. Это не демо и не прототип — проект активно
используется в бою, с реальными учётными данными Jira/GitLab/Telegram в
`.env`, реальными деньгами (Anthropic API через подписку), реальными MR в
`saqr/back-ai` и `saqr/front-ai`.

Технически — обёртка вокруг CLI `claude` (headless-режим, `-p
--output-format stream-json`), не SDK. Каждая роль в пайплайне — это один
вызов `claude` с конкретной моделью, конкретными разрешёнными/запрещёнными
инструментами, и либо изменяет файлы в git worktree (роль "разработчик"),
либо только читает код и возвращает структурированный текст, который движок
сам парсит и решает, что делать (роли PM/ревьюер/память/тестировщик —
read-only, `Bash,Edit,Write,MultiEdit` запрещены на уровне `claude`).

## 2. Путь одного тикета от Jira до MR — полная картина

```
Jira ("Сделать", назначено на тебя)
  │
  ▼
Telegram /start → список тикетов → клик по тикету
  │
  ▼
PROPOSE (PM, Sonnet, read-only)
  — читает код репозитория, пишет план + критерии приёмки
  — критерии ещё НЕ зафиксированы, это предложение
  │
  ▼
Telegram: план + критерии + оценка стоимости/времени по истории + кнопки
  ✅ Подтвердить / ❌ Отменить
  │
  ▼ (после "Подтвердить")
ACCEPTANCE TEST (Sonnet, write ровно один новый файл)
  — пишет src/__acceptance__/<ISSUE-KEY>.<ext>, по одному test() на критерий
  — тест должен ПАДАТЬ в этот момент (реализации ещё нет)
  — становится строгим гейтом, implement не может его редактировать
  │
  ▼
BASELINE — считает, сколько тестов/ошибок уже падает ДО правки
  │
  ▼
┌─── ЦИКЛ IMPLEMENT (разработчик, Opus, до MAX_ITERATIONS=5 раз) ───┐
│  claude редактирует файлы в своём git worktree                    │
│    │                                                               │
│    ├─ ответ — БРИФ? → пауза, вопрос в Telegram с кнопками,        │
│    │   возобновление той же сессии после ответа (см. §6)         │
│    │                                                               │
│    ▼                                                               │
│  гейты: typecheck / lint / test / build (baseline-сравнение)      │
│    │                                                               │
│    ├─ не прошло → фидбек по каждому упавшему гейту → следующая    │
│    │   итерация (или "stuck", если ошибка повторилась 2 раза      │
│    │   подряд одинаково — см. §7)                                 │
│    │                                                               │
│    ▼ прошло                                                       │
│  commit                                                            │
└──────────────────────────────────────────────────────────────────┘
  │
  ▼
ПРОВЕРКА ЦЕЛОСТНОСТИ ГЕЙТОВ (механически, без LLM)
  — не удалил ли агент тест, не добавил ли .skip, не трогал ли CI-конфиг
  — нашёл что-то → сразу "нужен человек", без повторной попытки
  │
  ▼ чисто
┌─── ЦИКЛ REVIEW (ревьюер, Opus, до MAX_REVIEW_ROUNDS=3 раундов) ───┐
│  читает весь дифф, ищет то, что гейты не ловят механически        │
│    │                                                               │
│    ├─ блокирующая находка → фикс в ТОЙ ЖЕ сессии implement        │
│    │   (--resume) → гейты заново → ревью снова                   │
│    │                                                               │
│    ├─ 3 раунда и ревьюер всё ещё недоволен → "нужен человек"      │
│    │                                                               │
│    ▼ доволен                                                      │
└──────────────────────────────────────────────────────────────────┘
  │
  ▼
TESTING NOTES (Sonnet, read-only) — пишет инструкцию для тестировщика
PROJECT MEMORY (Sonnet, read-only) — решает, есть ли долгоживущий факт для записи
  │
  ▼
push ветки → MR в GitLab → комментарий в Jira (MR + инструкция тестировщику)
  → перевод тикета в статус "Review"
  → уборка worktree/локальной ветки
```

Любой путь, где что-то пошло не так (исчерпаны итерации, застревание,
превышен бюджет контекста, ревью не удовлетворено после 3 раундов, не
удалось запушить/открыть MR) приводит к **единому механизму "нужен
человек"**: diff показывается в Telegram с кнопками ✅ Принять и
запушить / ❌ Отклонить. Это не "бот сломался" — чаще всего это реально
неоднозначная или нетривиальная задача.

## 3. Карта файлов

```
src/
  cli.ts              — точка входа (commander): run/queue/bot/eval/dashboard
  config.ts           — ЕДИНСТВЕННОЕ место чтения process.env, вся конфигурация
  types.ts            — все общие типы (TaskSpec, EngineConfig, CloseLoopResult, Brief, ...)
  queue.ts            — оркестрация: propose→approve→dispatch, cross-repo, резолв брифов/needs_human
  gitlab.ts           — push ветки + создание MR через GitLab API

  jira/
    client.ts         — HTTP-клиент Jira (Bearer PAT), парсинг ADF-описаний, addAttachment (multipart)
    mapToTask.ts       — detectRepo() по префиксу [backend]/[frontend]/[web], toTaskSpec()

  engine/             — ядро: всё, что реально выполняет работу
    claudeEngine.ts    — спавн `claude` CLI, парсинг stream-json, buildAgentEnv() (секреты из окружения)
    loop.ts            — runCloseLoop(): ГЛАВНЫЙ цикл реализации+верификации+ревью (см. §2)
    prompts.ts         — тексты промптов для implement (initial/feedback)
    proposal.ts        — парсинг ответа PM (план + критерии)
    acceptanceTest.ts  — write ровно одного тестового файла, проверка что тронут только он
    review.ts          — промпт/парсинг независимого ревью, buildReviewFixPrompt
    brief.ts           — парсинг БРИФ/ВОПРОС/ВАРИАНТЫ, buildBriefAnswerPrompt
    memory.ts          — чтение/запись project memory (по ролям: pm.md/dev.md/reviewer.md)
    testingNotes.ts    — инструкция для тестировщика
    closeReport.ts     — сводка для заказчика тикета, показывается в Telegram
    workReport.ts      — чистая композиция closeReport+testingNotes в файл-вложение Jira
    verify.ts          — baseline-сравнение гейтов (typecheck/lint/test/build)
    gateIntegrity.ts   — механическая проверка "не ослабил ли агент гейты"
    secretScrub.ts     — чистые функции скраба секретов из resultText read-only ролей
    stuckDetector.ts   — fingerprintFailure() для детектора застревания
    guardrails.ts      — DEFAULT_DENIED_PATHS (миграции/.env/CI/lock-файлы/ключи)
    checkpoint.ts      — механический checkpoint на диске, recoverOrphanedCheckpoints()
    agentContext.ts    — per-task/per-role scratch (.harness-state/tasks/<KEY>/<role>/)
    git.ts             — worktree create/remove, commitAll, getWorktreeDiff, deleteBranch, fetchFreshBase, rebaseOntoFreshBase

  bot/
    bot.ts             — ВСЯ Telegram-логика: команды, кнопки, персонаж "Зам. CEO", classifyMessage
    liveState.ts        — in-memory состояние текущей задачи + pending* (approval/humanReview/brief)
    state.ts            — персистентная история задач (bot-state.json), estimateCost(), computeMetrics()

  web/
    server.ts          — HTTP-сервер дашборда (localhost:4790)
    page.ts            — HTML/CSS/JS дашборда как строка (пиксель-арт-сцена, вкладки)

  evals/               — мини-бенчмарк на реальных исторических багах
    types.ts, loadCases.ts, gates.ts, runCase.ts, runSuite.ts, report.ts

evals/cases/*.json      — 3 кейса (реальные закрытые баги XEN-364/369/302)
.githooks/              — pre-commit (весь npm test) + commit-msg (требует *.test.ts в том же коммите)
.harness-state/         — ВСЁ рантайм-состояние на диске (см. §5), в .gitignore
```

Каждый `*.ts` файл в `src/engine/` и `src/bot/state.ts` имеет рядом
`*.test.ts` — устоявшийся паттерн: **чистая функция (парсинг/форматирование/
решение) вынесена отдельно от I/O-обёртки и протестирована юнит-тестом**;
I/O-обёртки (реальные вызовы `claude`, GitLab API, Jira API) не мокаются и не
тестируются напрямую — их корректность проверяется живыми прогонами и eval-
набором. Единственное заметное исключение — `src/bot/bot.ts` не имеет своего
test-файла (чистые функции форматирования там технически не экспортированы);
`src/queue.ts`'s главная оркестрация (`runJob`/`runCrossRepoJob`) тоже не
покрыта юнитами — только `splitCrossRepoCriteria`.

## 4. Роли и модели

| Роль | Файл | Модель (по умолчанию) | Доступ | Что делает |
|---|---|---|---|---|
| Классификатор чата | `bot.ts` (`classifyMessage`) | Haiku | read-only, без tools вообще | свободный текст в Telegram → intent |
| PM / propose | `queue.ts` (`proposeSolution`) | Sonnet | read-only (Edit/Write/Bash запрещены) | план + критерии приёмки |
| Разработчик / implement | `loop.ts` | Opus | полный доступ к файлам в worktree, Bash запрещён, deny-list путей | пишет фикс, может поднять БРИФ |
| Acceptance-test writer | `acceptanceTest.ts` | Sonnet | write ровно одного нового файла | тест из критериев приёмки |
| Ревьюер | `review.ts` | Fable 5.1 | read-only | ищет то, что гейты не ловят |
| Тестировщик (notes) | `testingNotes.ts` | Sonnet | read-only | инструкция Предусловия/Шаги/Результат |
| Докладчик (report) | `closeReport.ts` | Sonnet | read-only | сводка для заказчика тикета, не для разработчика/тестировщика |
| Память | `memory.ts` | Sonnet | read-only (возвращает текст, движок сам пишет файл) | решает, есть ли долгоживущий факт |

Опечатка в названии переменной недопустима — модель на роль задаётся через
`*_MODEL` в `.env`, полный список в `config.ts`. **Разработчик (Opus) и
ревьюер (Fable 5.1) теперь на разных моделях** — намеренно: тот же уровень
возможностей, но другая линейка, чтобы ревьюер не разделял слепые пятна
разработчика, тем же рассуждением, что у ЕТС Тендер.

Деньги/вызовы реальные — **каждый прогон стоит денег** через Anthropic API.
Это не локальная симуляция.

## 5. Что и где лежит на диске (`.harness-state/`, не версионируется)

```
.harness-state/
  bot-state.json           — вся история задач (issueKey, outcome, cost, duration, repo)
  pending-state.json       — что сейчас ждёт решения человека (approval/humanReview/brief), переживает рестарт
  checkpoints/<KEY>.json   — "процесс упал посреди итерации N" — recoverOrphanedCheckpoints() при старте
  tasks/<ISSUE-KEY>/
    reviewer/round-N.md    — что нашёл ревьюер в раунде N
    dev/round-N-response.md — чем ответил разработчик
  eval-runs/<timestamp>.json — результаты прогонов eval-набора

<repo>/.claude/memory/jira-harness/
  pm.md                    — заметки роли PM (пока никто не пишет, слот зарезервирован)
  dev.md                   — заметки роли разработчика (единственный реальный писатель сейчас)
  reviewer.md              — заметки роли ревьюера (пока никто не пишет)

<repo>/.claude/memory/MEMORY.md — ЧУЖОЕ, команды проекта; харнесс только читает, никогда не пишет
```

`worktree`-директории для задач создаются и удаляются динамически (`git
worktree add/remove`) рядом с основным чекаутом репозитория — не хранятся
долго, см. §8 "уборка worktree".

## 6. Ключевые механизмы, которые нужно понимать перед правками

Все подробно описаны в README.md; здесь — короткая справка "что это и зачем",
чтобы знать, куда смотреть.

- **Пауза и резюме (`resumeFrom` в `EngineConfig`, `CloseLoopResumeState`)**
  — используется брифами (все три места, см. ниже). `runCloseLoop` умеет не
  только идти от начала до конца, но и продолжаться с середины той же сессии
  `claude` (`--resume`), без пересчёта baseline/acceptance-теста. Если
  трогаешь `loop.ts` — помни, что есть три входа: с нуля, `resumeFrom` на
  основной цикл реализации, и `resumeFrom.reviewResume` на раунд правки по
  замечаниям ревью (`runPostImplementSuccess`) — все три должны остаться
  консистентными. **`CloseLoopResumeState.worktreeDir` обязателен не
  случайно** — был реальный баг (найден и исправлен при разборе самого
  механизма, не вживую на бою): без него резюме падало в `createWorktree()`,
  который форсированно пересоздаёт worktree по тому же пути — тихо стирая
  незакоммиченную работу итераций до паузы. Если когда-нибудь будешь менять
  resume-путь — `worktreeDir` должен прийти ПЕРВЫМ в приоритете перед
  `existingWorktreeDir`/`createWorktree`, не наоборот. Следом, на том же
  входе, идёт `rebaseOntoFreshBase()` (если `config.freshBase` включён) —
  пауза может длиться часы/дни, и ребейз на свежий `origin/<target>` при
  резюме — то, что реально держит ветку задачи неразошедшейся с `dev` к
  моменту финального пуша. Конфликт → `stopReason: "rebase_conflict"` →
  существующий флоу "нужен человек", worktree уже в чистом состоянии
  (`rebaseOntoFreshBase` сам откатывает ребейз при неудаче).
  `reviewResumeNowUnsafe()` (`loop.ts`, чистая функция, протестирована
  отдельно) закрывает смежный случай: если `REVIEW_ENABLED`/
  `MAX_REVIEW_ROUNDS` поменяли в `.env` и перезапустили бота, пока
  ревью-бриф висел — наивное продолжение молча проигнорировало бы уже
  данный человеком ответ и отрапортовало "verified", хотя блокирующая
  находка так и осталась неразрешённой. Вместо этого — та же эскалация
  "нужен человек", что у обычного `review_blocked`, с теми же находками.
- **Брифы** (`brief.ts`) — работают и в основном ходу implement, и в
  ревью-фикс-раунде (`runPostImplementSuccess` в `loop.ts`,
  `CloseLoopResumeState.reviewResume`), и для обеих половин кросс-репо задач
  (`CrossRepoBriefContext` в `types.ts`, `afterBackendAttempt`/
  `afterFrontendAttempt` в `queue.ts`) — везде один и тот же `PendingBrief`/
  `resolveBrief` механизм, разница только в том, что именно несёт
  `resumeState`/`crossRepo`.
- **Гейты baseline-relative vs strict** (`verify.ts`, `types.ts` `GateSpec.strict`)
  — typecheck/lint/test/build сравниваются "не хуже, чем было" (терпят уже
  существующий шум в репозитории); acceptance-тест и eval-скрытый тест —
  строгие, обязаны дать честный exit 0.
- **Единственная точка правды для секретов в окружении агента** —
  `SECRET_ENV_VARS` в `config.ts` + `buildAgentEnv()` в `claudeEngine.ts`.
  Если добавляешь новый секрет в `.env` — ОБЯЗАТЕЛЬНО добавь его в этот
  список, иначе он утечёт в окружение `claude` и будет читаем через Bash
  (если Bash когда-нибудь разрешат какой-то роли). Добавь его туда же и в
  `secretValues()` рядом с `SECRET_ENV_VARS` в `config.ts` — это вторая,
  отдельная защита (`secretScrub.ts` + `runClaudeTurn`), которая маскирует
  значение секрета, если read-only роль случайно прочитает его из файла/лога
  и скопирует в свой текстовый ответ (идёт в Jira/MR/память проекта).
- **Checkpoint живёт дольше, чем кажется** — не только на время итераций
  implement, но и через push/MR/комментарий в Jira (см. README "Checkpoint").
  Если добавляешь новый шаг после успеха (ещё один комментарий, ещё один
  внешний вызов) — подумай, нужен ли промежуточный checkpoint на этом шаге.

## 7. Известные пределы и сознательно отложенное (НЕ баги, не забытое)

Эти вещи обсуждались в сравнении с двумя референсными архитектурами —
**Avengers Harness** (внутренний дизайн-документ, многоагентная архитектура
с Mercury message bus, Postgres как источник правды, Docker-изоляция,
Explore QA) и **ЕТС Тендер "Флот ИИ-агентов"** (боевая система с почтой
между агентами, брифами, независимым аудитом, ~950 писем/день) — и
сознательно НЕ реализованы, потому что либо не стоят сложности при
однопроцессной архитектуре, либо требуют отдельного многодневного проекта:

- **Нет изоляции исполнения (Docker/контейнеры)** — агент и гейты работают
  напрямую на хосте с полным доступом к сети/ФС. Секреты вычищены из
  окружения агента (см. §6), но вредоносный код в тест-файле при прогоне
  гейтов всё ещё выполнялся бы с правами хоста.
- **Источник правды — JSON-файлы на диске, не Postgres/транзакции.** Для
  одного воркера без конкурентных задач это осознанно избыточно, но
  означает: узкое окно гонки между "перевели статус в Jira" и "обновили
  checkpoint" (секунды, не больше — см. README "Checkpoint").
- **Нет e2e/Explore QA.** Acceptance-тест — один unit/API-тест, никакого
  Playwright, никакого "попробовать сломать фичу специально".
  Соответственно, никаких скриншотов в отчётах.
- **Eval-набор всё ещё маленький** — 3 кейса. `eval --k N` (готово — см. §9
  history) даёт pass@1/pass^k вместо единственного pass/fail на кейс, но на
  3 кейсах один кейс по-прежнему весит слишком много: "модель А лучше модели
  Б" значимо только при крупном эффекте (выигрыш/проигрыш в большинстве
  кейсов), не при разнице в доли процента. Больше кейсов — по мере
  накопления показательных регрессий в back-ai/front-ai, не заранее
  (каждый кейс стоит реальных денег на каждый прогон, тем более на `k>1`).
- **Lessons/обучение на ошибках не реализовано** — project memory пишет
  факты о проекте, но нет механизма "агент сформулировал урок → trial на N
  следующих задачах → adopted/retired", как в дизайне Avengers.
- **Онбординг нового репозитория — вручную.** Третий репозиторий (не
  back-ai/front-ai) потребует ручной правки `config.ts` (`RepoKind`
  захардкожен на `backend`/`frontend`), а не скрипта-скана проекта.
- **Дашборд — только localhost**, доступ с телефона требует туннель
  (ngrok/cloudflared), не настроено.
- **Gate baseline не пересчитывается после ребейза при резюме.** Если
  `rebaseOntoFreshBase` (см. §6) реально подвинул HEAD, `config.resumeFrom.
  baselines` могут немного разойтись с текущей реальностью репозитория (dev
  мог и починить, и добавить что-то не по теме задачи между установкой
  baseline и паузой). Харнесс логирует это в `onLog`, но не пересчитывает:
  честный пересчёт означал бы прогнать гейты против чистого
  `origin/<target>` БЕЗ собственных коммитов/незакоммиченного задачи — сам
  ребейзнутый worktree их уже смешивает, и наивный `establishBaselines()`
  прямо там подмешал бы собственные правки агента (после autostash-пропа) в
  "существующий шум". Правильно — одноразовый disposable worktree только
  для замера; не сделано, т.к. эффект (небольшой сдвиг счётчика) низкой
  серьёзности и вероятности относительно стоимости лишнего прогона гейтов
  на каждом резюме с движением dev.
- **Проверка целостности гейтов всегда пропускается при резюме раунда
  ревью** (`skipGateIntegrityCheck: true` в `runPostImplementSuccess`,
  обоснованно — она уже прошла до паузы). Но если `GATE_INTEGRITY_CHECK_
  ENABLED` переключили с `false` на `true` между паузой и резюме (правка
  `.env` + рестарт бота, пока бриф висел), а агент успел ослабить гейт ДО
  паузы, пока проверка была выключена — это так и останется незамеченным.
  Узко (нужна именно эта последовательность событий) и не исправлено:
  честный фикс означал бы гонять эту проверку на каждом резюме раунда
  ревью заново, а не только когда она реально нужна.
- **`resolveHumanReview`'s принятое вручную "нужен человек" не попадает в
  историю/метрики вообще.** Найдено при добавлении текстового отчёта
  вложением: в отличие от `handleCloseLoopOutcome`/`afterFrontendAttempt`,
  результат `resolveHumanReview(true)` нигде не проходит через
  `recordOutcome`/`recordTask` (`bot.ts` просто шлёт "✅ запушено, ..." и
  не трогает `bot-state.json`). Задача остаётся в истории с исходным
  `needs_human`-статусом навсегда, даже если человек её принял и MR
  реально открылся — `/metrics` посчитает её как эскалацию, не как закрытую.
  Стоимость двух новых read-only ходов для отчёта-вложения (testingNotes/
  closeReport), добавленных в этот же `resolveHumanReview`, туда же не
  попадает — это не новая проблема, а расширение уже существовавшего
  пробела, не решённого в рамках этой задачи (отдельная, более широкая
  правка — нужно решить, что считать "закрытием" для `/metrics`: исходный
  needs_human или финальное ручное решение).

Если тебя просят "довести харнесс до уровня X" — сверься с этим списком
сначала, возможно, конкретный пункт уже обсуждался и сознательно отложен по
названной причине, а не просто забыт.

## 8. Как запускать и тестировать

```bash
npm install
cp .env.example .env   # заполнить реальными токенами — файл НЕ коммитить, он в .gitignore

npm run build
node dist/cli.js bot          # прод-режим: Telegram-бот + дашборд, сам поллит Jira (ACTIVE/IDLE_POLL_SECONDS)
node dist/cli.js queue        # один разовый пропозл тикета (только предлагает, не запускает) — для ручной отладки,
                               # НЕ для cron: `bot` сам поллит, пока запущен (см. §7)
node dist/cli.js dashboard    # только веб-дашборд, без Telegram
node dist/cli.js eval         # прогнать мини eval-набор
node dist/cli.js run --repo <path> --task '...' --verify "pnpm test"  # разовая задача вне Jira

npm run dev                   # tsx напрямую, без build (для разработки)
npm test                      # весь набор юнит-тестов (node:test + tsx)
```

**Git-хуки — включить один раз на машине:**
```bash
git config core.hooksPath .githooks
```
После этого `pre-commit` гоняет весь `npm test` перед каждым коммитом, а
`commit-msg` блокирует коммит, который трогает `src/**/*.ts` без
соответствующего `*.test.ts` в том же коммите (escape hatch — строка
`No-Test: <причина>` в сообщении коммита, не `--no-verify`).

**Конвенция коммитов, устоявшаяся за весь проект:**
- typecheck (`npx tsc -p tsconfig.json --noEmit`) чистый и `npm test`
  зелёный **перед** каждым коммитом, без исключений.
- Сообщение коммита заканчивается строкой
  `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` (конкретная
  модель/версия может отличаться — смотри на актуальную систему-подсказку
  в своей сессии, если ты агент, продолжающий эту работу).
- Коммиты атомарные по фиче — одна фича/фикс = один коммит, не пачка
  несвязанных изменений разом.
- README.md обновляется в том же коммите, что и фича (build-plan список в
  начале файла + отдельный `###`-раздел с деталями и обоснованием).
- На практике в этом проекте каждый коммит сразу пушился в
  `git@github.com:arrlleon/harness-bot.git` без отдельного запроса
  подтверждения на каждый push — это наблюдаемая практика именно в этом
  репозитории; если это не совпадает с твоими общими инструкциями на другой
  работе — уточни у пользователя для этого конкретного проекта, не
  переноси один стиль на другой автоматически.

**Паттерн добавления фичи**, устоявшийся за весь проект: новый файл в
`src/engine/` с чистыми функциями + `*.test.ts` рядом → вайринг в `types.ts`
(`EngineConfig`/`CloseLoopResult`) → вайринг в `loop.ts` → вайринг в
`config.ts` (модель + kill-switch, если это опциональный слой) →
вайринг в `queue.ts` (передать конфиг в `runCloseLoop`, обработать новый
`stopReason` в формировании текста причины) → обновить `bot.ts`/`liveState.ts`,
если нужен UI → обновить README.md (build-plan + раздел) → typecheck + test
→ commit + push.

## 9. Приоритетный бэклог (предложения, не обязательства)

Исходя из сравнения с Avengers Harness/ЕТС Тендер, по убыванию
соотношения ценность/усилие:

1. **Скриншоты для фронтенд-тикетов в докладе** — текстовая часть докладчика
   (`closeReport.ts`) готова (см. §4, §7 build-plan в README); скриншоты —
   осознанно отложенная расширение той же роли, не отдельная фича с нуля.
   Требует Playwright (новой тяжёлой зависимости в проекте, которой сейчас
   нет вообще) и решения, с какого стенда снимать (нужен реальный
   задеплоенный URL и доступы, которых харнесс сейчас не имеет).
2. Остальное из §7 — объёмнее, не на один присест.
